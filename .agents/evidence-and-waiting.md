# Evidence and waiting

Delivery dispatchers, orchestrators, implementers, code reviewers, and stack managers use this policy. Role boundaries, acceptance criteria, required validation, independent review, isolation, dependencies, concurrency, and model/effort policy still apply. A budget changes how evidence is retrieved, never how much relevant evidence must be inspected.

## Bound evidence before returning it

The limits are 12,000 characters per command result, file read, search, diff range, or GitHub response, and 24,000 characters combined per tool call or parallel batch, including labels and summaries. These are instructional limits, not runtime enforcement. No repository wrapper intercepts output. Character counts include whitespace and long lines. A 2,000-line limit alone is insufficient. Leave room below each limit for tool metadata. Token limits on tools are an additional runtime guard when available; they may truncate output and do not prove completeness or enforce these character budgets.

Before a potentially large read, inspect its size locally, then choose ranges, paths, or fields that fit both limits. For unknown-sized commands and GitHub responses, writers retain the complete result in an ignored worktree artifact or a temporary file outside tracked paths, count it locally, and return only bounded selected evidence. Keep private material out of commits and handoffs. Read-only roles keep evidence in existing Git objects, existing local artifacts, or the response held in a read-only pipeline's memory. They do not write scratch files or run project code. Select and count the text before printing it; on overflow print only the count and requested scope, then narrow the next retrieval. Preserve access to the full source, including pagination, rather than silently dropping the remainder. A response that cannot be retained can be retrieved again for missing fields or pages; that is recovery of new evidence.

For GitHub, request only the needed response fields with `--jq`, page list endpoints, and select the relevant issue, item, comments, or PR. A selected `body` can itself exceed the budget. Count it before returning it, then retrieve its relevant sections in bounded ranges. For source files and diffs, use path inventories and sizes followed by numbered ranges. For long single lines, use character ranges or structured fields and track their coverage. For validation, retain the complete log locally and return a bounded result summary and relevant failures. Do not hide a failed command behind a successful output-filter command.

Batch independent reads only when their combined returned text fits 24,000 characters. Share that budget across nested calls and their aggregate result; separate per-command caps do not cap an enclosing call. Keep dependent retrievals and mutations sequential. Splitting retrieval into several calls is appropriate when complete evidence needs more space.

Inspect tool metadata and output for truncation markers, omitted ranges, missing pages, or an unexpected size. Any of those means the evidence is incomplete. Recover every missing relevant range, match, field, or page before editing, judging, or reporting from it. Do not treat a clipped summary as a complete diff or a complete search. When the result fits and was not truncated, reuse it rather than repeating the command. Successful evidence is keyed by its inputs (path and content revision, diff base/head, query and response revision, or validation command and tested SHA). Re-read only changed regions with enough surrounding context after an edit, and search for other statements of a changed rule. Re-run an unchanged successful command only when there is concrete evidence its external source changed or when recovering missing evidence. Keep a compact ledger of inspected ranges and facts; do not paste the source again into a handoff.

## Wait for events

While a child is active and no independent authorized work remains, use the agent wait tool with the longest timeout permitted by the tool, runtime, and loaded instructions. For example, a tool allowing an hour with a loaded 60-second maximum means a 60-second wait. A lower runtime maximum wins. Blocking Agent calls already wait for completion; do not add polling around them. Use agent tools for agent completion and shell-session tools only to resume a running command.

Remain idle between completion, a substantive child message, user input, or a required progress-update deadline. A timeout alone is not new information. After a timeout, re-enter the longest permitted wait without status probes, repeated `list_agents`, output rereads, or status-only messages to children. Respond promptly to user steering. Preserve required user-facing progress updates at their loaded cadence; if an update is due with no new facts, send one brief update and resume waiting. This required update is the only exception to avoiding status-only messages. Where a runtime supports a shorter progress deadline than the maximum wait, use that deadline as the permitted timeout.

Send a child only new evidence, a decision, a correction, or an answer it needs. Do not wake it to ask whether it is still working. Record a completed result before dispatching dependent work. Preserve the orchestrator's recorded independence groups and concurrency limit. Never use shell sleep loops, shell polling, or remote-CI waiting, polling, or reruns to coordinate agents.
