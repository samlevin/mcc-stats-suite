# Bootstrap CDK and grant local deploy access

CDK bootstrap is separate from the OpenTofu bootstrap. Run it once in each account and workload Region, dev first, with the administrator profile:

```console
cd "$(git rev-parse --show-toplevel)"
export AWS_PROFILE=mcc-dev-admin
aws sso login --profile "$AWS_PROFILE"
aws sts get-caller-identity --profile "$AWS_PROFILE"
npx cdk bootstrap "aws://$(aws configure get sso_account_id)/$(aws configure get region)" \
  --cloudformation-execution-policies arn:aws:iam::aws:policy/AdministratorAccess
```

Verify the account ID before approving. The account ID and Region come from the profile's `sso_account_id` and `region`. For prod, enter the prod bootstrap directory so `direnv` loads the prod profile:

```console
cd infrastructure/prod/bootstrap
aws sso login --profile "$AWS_PROFILE"
aws sts get-caller-identity --profile "$AWS_PROFILE"
npx cdk bootstrap "aws://$(aws configure get sso_account_id)/$(aws configure get region)" \
  --cloudformation-execution-policies arn:aws:iam::aws:policy/AdministratorAccess
```

The `CDKToolkit` stack belongs to CDK. Do not import it into OpenTofu. The GitHub CDK entry role from the OpenTofu bootstrap can assume the account's `cdk-*` roles, which in dev also covers the local `cdk-mcclocal1-*` roles described below. Those roles are narrower than the `hnb659fds` roles, so this grants GitHub Actions nothing new.

`AdministratorAccess` is a broad starting execution policy. Anyone who can assume the CDK deploy role can deploy almost anything in that account. Replace it with a reviewed project policy once the application resource set is stable.

## Bootstrap local deployments separately

Keep the default `hnb659fds` bootstrap for GitHub Actions. Local developers use the separate `mcclocal1` bootstrap, generated by `scripts/local-cdk-bootstrap.mjs` from the CDK template pinned in `package-lock.json`.

The template defines the bootstrap roles and the staging bucket. It does not define the local permission policies: the execution role's three policies and boundary, and the workload boundary that every ephemeral role gets. The dev foundation creates those five policies (`infrastructure/modules/foundation/local-cdk-policies.tf`), and the template attaches them by name. Apply the dev foundation first, or the bootstrap fails because the policies do not exist. Then, as the dev administrator, verify the identity, create the bootstrap, and protect it:

```console
cd "$(git rev-parse --show-toplevel)"
aws sts get-caller-identity --profile mcc-dev-admin
npx cdk bootstrap --show-template | node scripts/local-cdk-bootstrap.mjs > /tmp/mcc-local-bootstrap.yaml
npx cdk bootstrap "aws://$(aws configure get sso_account_id --profile mcc-dev-admin)/$(aws configure get region --profile mcc-dev-admin)" \
  --profile mcc-dev-admin --qualifier mcclocal1 \
  --toolkit-stack-name CDKToolkitLocal --template /tmp/mcc-local-bootstrap.yaml
aws cloudformation set-stack-policy --profile mcc-dev-admin --stack-name CDKToolkitLocal \
  --stack-policy-body file://docs/self-hosting/policies/local-cdk-toolkit-stack-policy.json
aws cloudformation update-termination-protection --profile mcc-dev-admin \
  --stack-name CDKToolkitLocal --enable-termination-protection
```

A plain `cdk bootstrap --qualifier mcclocal1` without `--template` would give the local execution role the upstream `AdministratorAccess` policy and drop its boundary, and every local developer could then use it. The generated template adds a `LocalBootstrapGuard` resource that creates nothing and that the upstream template lacks. The [stack policy](policies/local-cdk-toolkit-stack-policy.json) stops any update from deleting or replacing it, so a plain bootstrap fails instead.

See [Local CDK bootstrap design](../local-cdk-bootstrap-design.md) for the allowed resources, known limits, and boundary validation procedure.

### Change the local permissions

The permissions belong to the dev foundation. Change `infrastructure/modules/foundation/local-cdk-policies.tf` and its tests in a pull request, and apply the dev foundation as for any other foundation change ([Apply and change the foundation](40-change-foundation.md)). The local roles get the change when the apply finishes. Do not re-run `cdk bootstrap`.

### Upgrade the local bootstrap

After a CDK upgrade or a change to `scripts/local-cdk-bootstrap.mjs`, always regenerate the template through `scripts/local-cdk-bootstrap.mjs` and pass it with `--template`, using the first three commands above. Never run `cdk bootstrap` for `mcclocal1` without `--template`. If the stack policy rejects an update, the template is missing `LocalBootstrapGuard`: fix the template instead of removing the stack policy.

### Remove the local bootstrap

1. Revoke the local permission set's assignments.
2. Destroy every ephemeral stack. Deleting the execution role first leaves the stacks without a role to delete them with.
3. Remove the stack policy and termination protection, then delete `CDKToolkitLocal`.
4. Empty and delete the retained `cdk-mcclocal1-*` staging bucket and ECR repository.

The five local permission policies stay with the dev foundation. Remove them there only after `CDKToolkitLocal` and every ephemeral stack are gone.

## Grant local deploy access

Developers deploy ephemeral stacks to dev from their own shells. Production deploys only from GitHub Actions. Do this after both dev CDK bootstraps.

1. In IAM Identity Center, create a group named `MccStatsSuiteLocalCdkDeployers`.
2. Create a custom permission set named `MccStatsSuiteLocalCdkDeploy` with a four-hour session. Do not attach `AdministratorAccess` or `PowerUserAccess`.
3. Copy [the policy template](policies/local-cdk-deployer-dev.json.template), replace every `DEV_ACCOUNT_ID` and `AWS_REGION` placeholder, and paste it as the permission set's inline policy. It allows assuming only the four `mcclocal1` CDK bootstrap roles and reading bootstrap metadata.
4. Assign the group and permission set to the dev account only. Never assign them to prod or to management accounts.
5. Add developers to the group, then point the `mcc-dev` SSO profile at this permission set.

Verify with an ephemeral stack:

```console
aws sso login --profile mcc-dev
aws sts get-caller-identity --profile mcc-dev
npm run app:diff -- match-to-csv --environment dev --ephemeral <name>
```

If CDK reports `sts:AssumeRole` denied, check that the role names in the policy match the `CDKToolkitLocal` account, Region, and `mcclocal1` qualifier. Do not fix the error with a broad AWS managed policy.

An `AccessDenied` that names `cdk-mcclocal1-cfn-exec-role` during a deploy, or `mcc-stats-suite-local-workload-boundary` at runtime, means the local policy lacks an action the application needs. Extend it as described in [Change the local permissions](#change-the-local-permissions). Never re-run the default bootstrap.
