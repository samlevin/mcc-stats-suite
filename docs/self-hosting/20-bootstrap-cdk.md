# Bootstrap CDK and grant local deploy access

CDK bootstrap is separate from the OpenTofu bootstrap. Run it once in each account and workload Region, dev first, with the administrator profile:

```console
cd "$(git rev-parse --show-toplevel)"
export AWS_PROFILE=mcc-dev-admin
aws sso login --profile "$AWS_PROFILE"
aws sts get-caller-identity --profile "$AWS_PROFILE"
npx cdk bootstrap "aws://$(aws configure get sso_account_id)/$(aws configure get region)" \
  --cloudformation-execution-policies arn:aws:iam::aws:policy/AdministratorAccess
```

Verify the account ID before approving. The account ID and Region come from the profile's `sso_account_id` and `region`. For prod, enter the prod bootstrap directory so `direnv` loads the prod profile:

```console
cd infrastructure/prod/bootstrap
aws sso login --profile "$AWS_PROFILE"
aws sts get-caller-identity --profile "$AWS_PROFILE"
npx cdk bootstrap "aws://$(aws configure get sso_account_id)/$(aws configure get region)" \
  --cloudformation-execution-policies arn:aws:iam::aws:policy/AdministratorAccess
```

The `CDKToolkit` stack belongs to CDK. Do not import it into OpenTofu. The GitHub CDK entry role from the OpenTofu bootstrap can assume the account's `cdk-*` roles, which in dev also covers the local `cdk-mcclocal1-*` roles described below. Those roles are narrower than the `hnb659fds` roles, so this grants GitHub Actions nothing new.

`AdministratorAccess` is a broad starting execution policy. Anyone who can assume the CDK deploy role can deploy almost anything in that account. Replace it with a reviewed project policy once the application resource set is stable.

## Bootstrap local deployments separately

Keep the default `hnb659fds` bootstrap for GitHub Actions. Local developers use the separate `mcclocal1` bootstrap, generated by `scripts/local-cdk-bootstrap.mjs` from the CDK template pinned in `package-lock.json`. As the dev administrator, verify the identity, create the bootstrap, then protect it:

```console
cd "$(git rev-parse --show-toplevel)"
aws sts get-caller-identity --profile mcc-dev-admin
npx cdk bootstrap --show-template | node scripts/local-cdk-bootstrap.mjs > /tmp/mcc-local-bootstrap.yaml
npx cdk bootstrap "aws://$(aws configure get sso_account_id --profile mcc-dev-admin)/$(aws configure get region --profile mcc-dev-admin)" \
  --profile mcc-dev-admin --qualifier mcclocal1 \
  --toolkit-stack-name CDKToolkitLocal --template /tmp/mcc-local-bootstrap.yaml
aws cloudformation set-stack-policy --profile mcc-dev-admin --stack-name CDKToolkitLocal \
  --stack-policy-body file://docs/self-hosting/policies/local-cdk-toolkit-stack-policy.json
aws cloudformation update-termination-protection --profile mcc-dev-admin \
  --stack-name CDKToolkitLocal --enable-termination-protection
```

The [stack policy](policies/local-cdk-toolkit-stack-policy.json) stops any update from deleting or replacing the local policies. A plain `cdk bootstrap --qualifier mcclocal1` without `--template` would otherwise replace the local roles' policies with the upstream `AdministratorAccess` execution policy, which every local developer can then use.

### What the local bootstrap allows

Ephemeral synthesis selects this bootstrap, its runtime boundary, and the IAM role path `/mcc-local/` automatically.

- **Deployment role.** It changes only stacks named `<application>-e-<name>`; shared stacks are outside its grants. Stack creates and updates must pass the local execution role, and it executes only change sets named `mcclocal1-deploy`. It reads only the bootstrap version and `/mcc/dev/*` application parameters.
- **Execution role.** Its scoped grants are split across three identity policies, and a boundary caps it at those services while denying CloudFormation, STS, and identity administration. It manages Lambda functions, state machines, queues, log groups, and EventBridge rules only by name under the `<application>-e-` prefixes. Rules may match only S3 events and may target only ephemeral compute. It creates roles only under `/mcc-local/` and only with the local runtime boundary, and it changes or passes only roles under that path. A role's path cannot change, so roles from before the local bootstrap, or made by hand, stay out of reach.
- **Runtime boundary.** It denies deployment and identity administration. It allows S3 writes and listing only under `ephemeral/<name>/`, and reads only under `ephemeral/<name>/` and `incoming/<name>/`, in buckets of this account. `<name>` is the `Ephemeral` tag CDK applies to the stack's roles. It allows invoking or starting only ephemeral application compute, using KMS keys only through S3, and reading single `/mcc/dev/*` parameters, such as the sender allowlist and submission address that `process-email` checks. Everything under `/mcc/<environment>/` is application config, so CI parameters such as the Turbo cache contract live under `/mcc-ci/` instead ([SSM parameter namespaces](../../infrastructure/README.md#ssm-parameter-namespaces)).
- **Lookup role.** It has no AWS managed policy and reads only stack metadata and the bootstrap version, because this repository makes no context lookups.
- **Trust.** Only principals of this account can assume the local roles, even if the bootstrap is run with `--trust`.

For ephemeral deploys, `scripts/cdk-app.mjs` passes `--change-set-name mcclocal1-deploy` and `--toolkit-stack-name CDKToolkitLocal` and rejects options that would bypass them ([details](50-deploy-and-release-applications.md)). Those checks only fail early; IAM refuses each option anyway.

This policy covers the currently implemented resources. Review and extend it when an application introduces a new AWS resource type, and never replace it with `AdministratorAccess`.

### Known limits

- SES receipt-rule APIs do not support IAM resource scoping, so the execution role creates, updates, deletes, and describes receipt rules on `*` for ephemeral email routes. It cannot change or activate receipt rule sets, but it does not isolate rule contents from arbitrary local templates.
- The per-developer S3 prefixes rely on the `Ephemeral` role tag. The execution role can tag any ephemeral role, so a deliberately crafted template can claim another developer's tag and reach their `ephemeral/<name>/` and `incoming/<name>/` objects.
- The file-publishing role is left as CDK ships it and can overwrite any object in the local staging bucket. CDK skips uploading an asset whose content hash already exists, so one developer can replace an asset that another developer's next deploy reuses.
- An ephemeral S3 rule can match object-created events for any bucket, so object keys and sizes in the shared buckets are visible to it. Object contents are not.

These limits keep developers from accidentally affecting each other and from changing shared dev; they do not isolate developers from each other. The bootstrap's IAM policy names are account-wide, matching the shared workload boundary, so bootstrap one Region per account.

### Upgrade the local bootstrap

After a CDK upgrade, always regenerate the template through `scripts/local-cdk-bootstrap.mjs` and pass it with `--template`, using the first three commands above. Never run `cdk bootstrap` for `mcclocal1` without `--template`. If the stack policy rejects an update, the template is missing a local policy: fix the template instead of removing the stack policy.

### Remove the local bootstrap

1. Revoke the local permission set's assignments.
2. Destroy every ephemeral stack. Their runtime roles use the local boundary, so the toolkit stack cannot be deleted while they exist, and deleting the execution role first leaves the stacks without a role to delete them with.
3. Remove the stack policy and termination protection, then delete `CDKToolkitLocal`.
4. Empty and delete the retained `cdk-mcclocal1-*` staging bucket and ECR repository.

## Grant local deploy access

Developers deploy ephemeral stacks to dev from their own shells. Production deploys only from GitHub Actions. Do this after both dev CDK bootstraps.

1. In IAM Identity Center, create a group named `MccStatsSuiteLocalCdkDeployers`.
2. Create a custom permission set named `MccStatsSuiteLocalCdkDeploy` with a four-hour session. Do not attach `AdministratorAccess` or `PowerUserAccess`.
3. Copy [the policy template](policies/local-cdk-deployer-dev.json.template), replace every `DEV_ACCOUNT_ID` and `AWS_REGION` placeholder, and paste it as the permission set's inline policy. It allows assuming only the four `mcclocal1` CDK bootstrap roles and reading bootstrap metadata.
4. Assign the group and permission set to the dev account only. Never assign them to prod or to management accounts.
5. Add developers to the group, then point the `mcc-dev` SSO profile at this permission set.

Verify with an ephemeral stack:

```console
aws sso login --profile mcc-dev
aws sts get-caller-identity --profile mcc-dev
npm run app:diff -- match-to-csv --environment dev --ephemeral <name>
```

If CDK reports `sts:AssumeRole` denied, check that the role names in the policy match the `CDKToolkitLocal` account, Region, and `mcclocal1` qualifier. Do not fix the error with a broad AWS managed policy.

An `AccessDenied` that names `cdk-mcclocal1-cfn-exec-role` during a deploy, or `mcc-stats-suite-local-workload-boundary` at runtime, means the local policy lacks an action the application now needs. Extend `scripts/local-cdk-bootstrap.mjs`, then upgrade the local bootstrap as above. Never re-run the default bootstrap.

## Validate the boundary

Use a disposable dev account with the dev foundation applied, and never run destructive denial probes against shared dev. Sign in with the local permission set and verify the identity, then:

1. Deploy, diff, and destroy `match-to-csv-e-<name>` through the wrapper, once with a 20-character name so generated resource names keep the application prefix. Send a message to `<alias>+<name>@<domain>` and confirm the workflow runs.
2. Run `cdk deploy` and `cdk destroy` targeting `admin-dev`, and `aws cloudformation update-stack` and `delete-stack` targeting every `<application>-dev`. Each write must return `AccessDenied`.
3. In policy simulation, check that `ExecuteChangeSet` for `cdk-deploy-change-set` is denied. Also check the execution role: it must be denied passing the default execution role, removing a runtime boundary, creating a role outside `/mcc-local/` or without the local boundary, and putting an EventBridge target on a `*-dev*` resource.
4. Run `cdk bootstrap --qualifier mcclocal1 --toolkit-stack-name CDKToolkitLocal` without `--template` and confirm the stack policy rejects the update.

After setting up local access, verify that a merge to `main` still deploys shared dev through GitHub Actions. The AWS-free tests in `scripts/local-cdk-bootstrap.test.mjs` evaluate the generated policies and synthesize every application; they do not replace this live validation.
