# Gamertag Roster: Technical Specification

**Status:** Draft; not implemented

**Version:** 1.0-draft

**Date:** October 15, 2026

**Component:** the operator roster script `scripts/roster.mjs` and the account check it shares with `scripts/cdk-app.mjs`; player name resolution in `applications/match-to-csv` (`extract-text`, `write-extracted-csv`, CSV format); a new pure package `packages/roster` (`@mcc/roster`); roster and resolution types in `packages/contracts`; the roster table in `infrastructure/modules/foundation`; ephemeral-stack permissions in `scripts/local-cdk-bootstrap.mjs`

**Runtime:** TypeScript, Node.js 22 on AWS Lambda (ARM64); the roster script runs on Node.js 22 with the AWS CLI on an administrator's machine

**Deployment:** resolution ships in the existing `match-to-csv` stack, one per stable environment from GitHub Actions plus ephemeral developer stacks, through the guarded wrapper in `scripts/cdk-app.mjs`; the roster script deploys nothing

**Input:** gamertags entered by an administrator through the roster script, and the parser rows `extract-text` produces for each run ([spec 1.1](1.1-mcc-analytics-engine.md) §8)

**Persistent state:** an append-only roster change log in one DynamoDB table per environment, owned by the OpenTofu foundation and encrypted with the foundation application data key; immutable roster snapshots and per-row resolutions in the OpenTofu-owned evidence bucket

**External dependencies at runtime:** DynamoDB, S3, KMS, SSM Parameter Store, STS (`GetCallerIdentity`, from the roster script and the evaluation script only); the evaluation script also uses the backlog roster API (§9.3): a Lambda function URL with IAM authentication, found through CloudFormation `DescribeStacks`

**Out of scope:** player identity across gamertags and renames (the stats lakehouse, #159), consent to publish statistics (§1), a roster screen in the reviewer application, rewriting OCR text in normalized observations, correcting team, score or outcome values, resolving names in tables the parser did not select, and resolving names of runs written before this component without a replay

In the two Halo 3 capture fixtures (§9.1), Textract reads 14 of 16 gamertags exactly. The two misreads are a look-alike character and a spacing error, which a comparison ignoring case, spaces and look-alike characters undoes. An administrator keeps a roster of the league's known gamertags. Each `extract-text` run compares every player name it reads with the roster, records the result beside the name as read, and writes the roster gamertag into the CSV with a `PlayerMatch` column that says whether the name matched exactly, was resolved from a near reading, or matched nothing.

**Readiness:** this specification authorizes filing Phases 0 to 4, except P2.1 to P2.3, which are backlog (§20). P3.1 cannot merge until P1.1 is applied in dev and prod, and the roster script writes an environment's roster only once P1.1 is applied there. The contracts in §10.1 freeze when P0.1 merges, and the thresholds in §7.3 stay initial values until P4.2 records the first check.

## 1. Resolved requirement decisions

Issue #163 lists the decisions this table records.

| Requirement | Decision | Reason |
| --- | --- | --- |
| Where the roster is stored | One DynamoDB table per environment, `<project>-<env>-gamertag-roster`, created by the OpenTofu foundation with deletion protection, point-in-time recovery, `prevent_destroy` and server-side encryption with the foundation data key `alias/<project>-<env>-application-data` (§13.2). The foundation publishes its name and ARN under `/mcc/<env>/roster/`. CDK stacks only read those parameters and grant their Lambdas access. | The roster outlives every application stack, so OpenTofu owns it like the evidence bucket. DynamoDB gives the conditional transaction that serializes changes (§6.1). The evidence bucket is under Object Lock and suits immutable records, which is where snapshots go (§5.2), but not a mutable head pointer. |
| How roster changes are recorded | The table is an append-only log. Each change is one `roster-change/v1` item, numbered from 1 without gaps, recording the action, the gamertag, the caller's IAM principal, an optional reason and the roster hash after the change. A `HEAD` item holds the latest version. A change item is never updated or deleted. The roster at version `v` is the fold of changes 1 to `v` (§5.1). | The log answers "who changed what, when" without a second store, and any version can be rebuilt exactly. A separate current-state item would be a second copy that can disagree with the log. |

The snapshot keeps the run reproducible if the table is ever restored from a backup or lost. |

Case folding before the look-alike map makes every case variant of a name share one key. Folding `i` with `l` merges a few real names; the conflict check catches those on the roster (next row). |
| How the roster refuses two gamertags that share a key | An add or reactivate whose key equals an active entry's key is refused with `409 KEY_CONFLICT`, naming the entries. There is no override, so no two active entries ever share a key. An add whose gamertag equals any entry's, active or inactive, ignoring case is refused with `409 DUPLICATE_GAMERTAG` instead, because Xbox gamertags are unique ignoring case. When two real players' gamertags share a key, the operator adds at most one of them; a reading of the other's name then resolves to the one on the roster (§18.4). | #163 requires the roster to refuse two gamertags that share a key. Most conflicts are an operator typing the same player twice, which the refusal catches. With one active entry per key, a key-equal reading has exactly one candidate, so §7.3 never has to choose between key-equal entries. The cost falls on real players whose names fold together, which §18.4 accepts and the `PlayerMatch` column and spec 2.3 review expose. |
| The near-match rule | The reading's key is compared with every active entry's key by Levenshtein distance. A unique best entry is chosen when its distance `d1` is within its budget, `min(2, floor(keyLength / 5))` (0 edits for keys of 1 to 4 characters, 1 for 5 to 9, 2 for 10 or more), and the runner-up distance `d2` is at least `d1 + 1` when `d1` is 0 and at least `d1 + 2` otherwise (§7.3). These are initial values (§9). | Both observed misreads need no edits once keys are compared, so nothing yet supports any edit budget. Short names get no edits, and a near match needs a two-edit lead, because the worst outcome is an unknown player resolved to a known gamertag one edit away. Key-equal readings keep the one-edit margin, which the placeholder fixtures need (§9.1). |

After each row is resolved on its own, an entry claimed by an `EXACT` row cannot also be the `RESOLVED` entry of another row, and an entry that two or more rows would resolve to resolves none of them. Those rows become `UNMATCHED` with `ENTRY_CLAIMED` (§7.4). | A gamertag appears once per scoreboard. Choosing a winner between two near readings would need a second-best assignment rule with no evidence behind it; refusing both is safe and rare. Two rows that read the same name exactly stay `EXACT`, because the roster changed nothing, and spec 2.1 `H001_DUPLICATE_PLAYER` flags them. |
| How an unmatched name is handled | Passed through as read and marked `UNMATCHED` with a reason. It does not hold the run, and it adds no `reviewFlags` code. | An unmatched name is usually a correct reading of a player who is not on the roster, so marking it "possibly misread" would be wrong. Spec 2.3 reviews every cell of every run anyway (spec 2.3 §7.1), so holding the run would delay the CSV without adding review. #161's flags still mark low-confidence readings (§8.1). |

The CSV header becomes `Team,Player,Score,Kills,Assists,Deaths,Win,Loss,PlayerMatch`. `PlayerMatch` holds `EXACT`, `RESOLVED` or `UNMATCHED`. `Player` holds the roster gamertag for `EXACT` and `RESOLVED` rows and the name as read for `UNMATCHED` rows (§7.6). **Additional capabilities included:** idempotent changes through a client request ID, a warning on add that lists active gamertags one key edit away, a change history command, per-run match counts in the run completion, and an evaluation script that measures the thresholds on real captures against the roster held in AWS, without writing the roster to disk or committing any name (P4.1).

## 2. Goals and non-goals

### 2.1 Goals

1. A reading of a roster gamertag that differs only by case, spacing or the look-alike groups in §7.1 appears in the CSV as the roster gamertag, marked `RESOLVED`.
2. Every resolution is recorded beside the name as read with the chosen gamertag, the distances, the error types and the roster version, and no stage changes the name as read.
3. Any run's resolution can be reproduced from its normalized observations and its roster snapshot.
4. Every roster change is an immutable record with the caller's IAM principal, and the roster at any version can be rebuilt from those records.
5. A reading near two roster gamertags, or near a known gamertag but not near enough, is never resolved.
6. Roster contents are stored only in AWS and never enter the repository.

### 2.2 Non-goals

- Correcting any value other than the player name in the CSV, or any value in normalized observations.
- Deciding which person a gamertag belongs to, linking renamed gamertags, or grouping screenshots into matches (#159).
- Recording or enforcing consent (§1).
- Holding a run, or skipping review, because of a match status. Spec 2.3 reviews every cell.
- Resolving names in runs written before P3.2, except through replay.
- Measuring the thresholds before captures exist. §9 sets out how they are checked.

## 3. Runtime architecture

```text
Administrator, mcc-<env>-admin profile
  |
  v
scripts/roster.mjs: account check, fold, checkChange (@mcc/roster)
  |  AWS CLI with the checked profile
  |
  +--reads; TransactWriteItems (HEAD condition)------------> Roster table (OpenTofu)
                                                              pk ROSTER#<namespace>
                                                              sk HEAD, CHANGE#<version>
                                                                 ^
match-to-csv ExtractText Lambda                                  |
  1.   manifest, RUN_STARTED                                     |
  2-3. read image, verify hash                                   |
  4.   read roster (consistent GetItem HEAD, Query CHANGE) ------+
       write roster snapshot (create-only) ----------> Evidence bucket roster/versions/
  5.   Textract AnalyzeDocument
  6.   parse -> resolvePlayers (@mcc/roster) -> normalized/observations.json
  7.   completion with roster reference and match counts
  |
  v
WriteExtractedCsv Lambda -> export/extracted.csv (PlayerMatch column), export/extracted-table.json
```

**Ownership rules:** the roster script is the only writer of the roster table. `extract-text` only reads the table and is the only writer of roster snapshots. `write-extracted-csv` only renders the run's normalized observations and what `extract-text` returned. `@mcc/roster` is pure: it performs no I/O, reads no clock and holds no state. Only Lambda entry points and the default dependencies of the roster script and the evaluation script reach AWS, the Lambdas through SDK clients and the roster script through the AWS CLI; core functions receive injected dependencies.

**Packaging:** `@mcc/roster` (`packages/roster`) exports the matcher and fold. `@mcc/contracts` exports the roster and resolution types (§10.1). The roster script is `scripts/roster.mjs`, beside `scripts/cdk-app.mjs`, and both import the account check from `scripts/account-guard.mjs`. Resolution in `match-to-csv` is a call into `@mcc/roster` from `extract-text`, with the table reader in `src/lib/roster-source.ts`.

**Orchestration decision:** no new workflow. Resolution adds one stage to an existing Lambda, and each roster change is one synchronous transaction.

### 3.1 Execution policy

- One roster change is one transaction and one new version. Changes in one namespace are serialized by the condition on `HEAD` (§6.1).
- One run reads exactly one roster version and resolves every player row of its selected table against it.
- Change items are created once with `attribute_not_exists` and never updated or deleted. Snapshots are written with `If-None-Match: *`.
- A failed roster read fails the run before Textract is called. Step Functions retries transient errors as spec 1.1 §6.3 lists; a retried extraction is a new run that reads the roster again.
- Stacks take their namespace from their deployment (§13.3), and the roster script from its `--ephemeral` option (§4.2).
- Resolution never changes the name as read, and never adds, drops or reorders rows.

## 4. Roster administration interface

The roster script (§4.2) is the v1 interface. The API in §4.1 is backlog (P2.1, P2.2); the script performs the same operations directly against the table, with the same checks and change records.

### 4.1 API routes

The `RosterAdmin` function URL, when P2.1 and P2.2 land, serves these routes. `RosterAdmin` routes on method and path, and returns `404 ROUTE_NOT_FOUND` for anything else. Every request carries a SigV4 signature that Lambda checks before the function runs, and Lambda lets it through only when the caller is allowed both `lambda:InvokeFunctionUrl` and `lambda:InvokeFunction` (§13.4); the handler reads the caller from `requestContext.authorizer.iam.userArn`. Request bodies are JSON of at most 4 KiB.

| Method and path | Body | Behavior |
| --- | --- | --- |
| `GET /v1/gamertags?status=ACTIVE\|INACTIVE\|ALL` | none | Entries of the current roster with `gamertagId`, `gamertag`, `status`, `matchKey` (computed with the deployed matcher), `addedVersion` and `lastChangedVersion`, sorted by gamertag ignoring case, plus `rosterVersion` and `rosterSha256`. `status` defaults to `ACTIVE`. |
| `GET /v1/changes?afterVersion=0&limit=100` | none | Change records with `rosterVersion` greater than `afterVersion`, oldest first, at most `limit` (1 to 500), and `nextAfterVersion` when more exist. |
| `POST /v1/gamertags` | `{ gamertag, reason?, clientRequestId }` | Adds an active entry with a new `gamertagId` (`evidenceId()`, spec 1.1 §5.1). |
| `POST /v1/gamertags/{gamertagId}/deactivate` | `{ reason?, clientRequestId }` | Marks an active entry inactive. It stays in the history and can be reactivated. |
| `POST /v1/gamertags/{gamertagId}/reactivate` | `{ reason?, clientRequestId }` | Marks an inactive entry active again, after the same key check as an add. |

A successful write returns `201` with `{ change, entry, rosterVersion, rosterSha256, warnings }`. `warnings.nearKeyGamertags` lists active gamertags whose key is one edit from the new entry's key, so the operator knows readings between them will be ambiguous. A write whose `clientRequestId` already appears in the log is a replay: it returns that change with `200` and writes nothing.

### 4.2 Roster script

```text
npm run roster -- --environment <dev|prod> [--ephemeral <name>] [--profile <profile>] <command>

list [--inactive | --all]
history [--after <version>]
add <gamertag>... [--reason <text>] [--yes]
deactivate <gamertag> [--reason <text>] [--yes]
reactivate <gamertag> [--reason <text>] [--yes]
```

- `--environment` is required. Before any other AWS call, the script runs the account check of `scripts/cdk-app.mjs`, from `scripts/account-guard.mjs`, which both import: a profile from `--profile` or `AWS_PROFILE` is required; the expected account is `MCC_DEV_ACCOUNT_ID` or `MCC_PROD_ACCOUNT_ID` for the chosen environment, or the profile's `sso_account_id` when that variable is unset, and must be 12 digits; the STS caller account must equal it; and a profile whose name implies the other environment is refused. A refused account sends no other request. `--ephemeral` is refused with `prod`, and ephemeral names follow the CDK wrapper's rule.
- Every AWS call runs through the AWS CLI with the checked profile, so the caller the check accepted is the one that writes. Its STS caller ARN is the change record's `actorArn`.
- It reads the table name from `/mcc/<env>/roster/table-name` and reads and writes only the `ROSTER#stable` partition, or `ROSTER#ephemeral/<name>` with `--ephemeral`. It queries the change items in pages of at most 100, passing each page's `NextToken` to the next query, so no single AWS CLI response holds the whole log.
- `list` prints the roster's version and hash, then each entry with `gamertag`, `status`, `gamertagId`, `matchKey`, `addedVersion` and `lastChangedVersion`, sorted by gamertag ignoring case. It shows active entries unless `--inactive` or `--all` is given. `history` prints the change records after `--after`, 0 by default, oldest first. Both fold the log and check its hash first (§6.1 step 2).
- Each write follows §6.1 and refuses the change with the `checkChange` result from `@mcc/roster` (§4.3). It prints the refusal code and the entries it names, or, after a write, the new version and any near-key warning.
- `deactivate` and `reactivate` take a gamertag and find its entry by a case-insensitive exact match, as `list --all` shows it. No match, or more than one, is refused with `GAMERTAG_NOT_FOUND` before any write.
- `add` with several gamertags writes one change per gamertag, in order, and stops at the first refusal.
- Every write generates a UUID `clientRequestId`, and every retry in §6.1 reuses it. A retry whose ID is already in the log writes nothing, so a transaction whose response was lost is not applied twice.
- Writes against `prod` print the change and ask for confirmation unless `--yes` is given. Any answer but `yes` writes nothing.
- The script reads gamertags only from its arguments and prints them only to the terminal. It reads no input file and writes no file.
- Exit status is 0 on success; 1 on a refused change, which includes `CONCURRENT_CHANGE` and a declined confirmation; and 2 on a usage, account, transport or `ROSTER_INTEGRITY` error.
- It needs `sts:GetCallerIdentity`, `ssm:GetParameter` on the table-name parameter, `dynamodb:GetItem`, `dynamodb:Query` and `dynamodb:PutItem` (inside `TransactWriteItems`) on the roster table, and the data key through DynamoDB. The `mcc-<env>-admin` profiles allow all of them, and no other operator policy is granted (§13.4).

### 4.3 Validation and errors

A gamertag is trimmed, runs of whitespace become one space, and the result must match `^[A-Za-z0-9 ]{1,16}(#[0-9]{1,4})?$`, which is spec 2.1's default `playerNamePattern` (spec 2.1 §7.2, `C003`). `reason` is at most 256 characters. `clientRequestId` is a UUID. A body holds only the fields §4.1 lists for its route; any other field, such as an actor or an override, fails the schema.

| Condition | Status and code | Writes |
| --- | --- | --- |
| Body fails the schema, or the gamertag fails the pattern | `400 INVALID_REQUEST`, `400 INVALID_GAMERTAG` | nothing |
| No `gamertagId` in the roster | `404 GAMERTAG_NOT_FOUND` | nothing |
| An entry, active or inactive, has the same gamertag ignoring case | `409 DUPLICATE_GAMERTAG`, with that entry | nothing |
| An active entry shares the key, on add or reactivate; there is no override | `409 KEY_CONFLICT`, with the entries | nothing |
| Deactivating an inactive entry, reactivating an active one | `409 ALREADY_INACTIVE`, `409 ALREADY_ACTIVE` | nothing |
| The `HEAD` condition failed on 3 attempts in a row | `409 CONCURRENT_CHANGE` | nothing |
| The fold of the log does not match `HEAD` (§6.1 step 2) | `500 ROSTER_INTEGRITY`, logged at `ERROR` | nothing |
| Any other storage error after the AWS CLI's or SDK's retries | `503 UNAVAILABLE`; the roster script exits 2 | nothing; the roster script retries with the same `clientRequestId` (§6.1) |

## 5. Storage and run records

### 5.1 Roster table

| Item | `pk` | `sk` | Attributes |
| --- | --- | --- | --- |
| Head | `ROSTER#<namespace>` | `HEAD` | `rosterVersion`, `rosterSha256`, `updatedAt` |
| Change | `ROSTER#<namespace>` | `CHANGE#<rosterVersion, 10 digits>` | every `RosterChange` field (§10.1) |

`<namespace>` is `stable` for stable stacks and `ephemeral/<name>` for ephemeral ones. A namespace with no `HEAD` item has version 0 and an empty roster.

**Fold.** The roster at version `v` starts empty and applies changes 1 to `v` in order. `ADD` creates an active entry, `DEACTIVATE` makes one inactive and `REACTIVATE` makes one active again. A gap in versions, an `ADD` of an existing `gamertagId`, or an action on an entry in the wrong state fails the fold with `RosterIntegrityError`.

**Hash.** `rosterSha256` is the SHA-256 of the UTF-8 JSON array of active entries `{ "gamertag", "gamertagId" }`, sorted by `gamertagId` bytewise, with object keys sorted and no whitespace. The empty roster hashes `[]`. Inactive entries do not affect the hash, because matching never reads them.

### 5.2 Evidence layout

```text
[ephemeral/<name>/]roster/versions/{rosterVersion}.json
[ephemeral/<name>/]submissions/{submissionId}/screenshots/{screenshotId}/runs/{runId}/
  normalized/observations.json        roster reference; parser.rows[].playerResolution
  completion.json                     roster reference; metrics.playerMatchCounts
  export/extracted-table.json         roster reference; rows[].playerResolution
  export/extracted.csv                PlayerMatch column
```

`{rosterVersion}` is zero-padded to 10 digits, so keys sort in version order. Version 0 has a snapshot with no entries.

### 5.3 Rules

1. Change items are created once and never updated or deleted. The `HEAD` item is the only item that changes.
2. A snapshot's bytes are a deterministic function of the namespace and version, with no timestamp, so every writer of a version produces the same object.
3. `extract-text` records a roster version on a run only after that version's snapshot exists and its `rosterSha256` matches.
4. A resolution never changes `observedText`, `parser.rows[].player` or any other value as read.
5. Every run records `rosterMatcherVersion` in its manifest `versions`, and the roster reference in its normalized observations, completion and export.

### 5.4 Document schemas

`normalized-ocr/v2`, `processing-run-completion/v1` and `extracted-table/v1` gain optional fields only, like `reviewFlags`, so documents written before P3.1 still validate.

| Object | `schemaVersion` | Writer | Contents |
| --- | --- | --- | --- |
| roster table change item | `roster-change/v1` | the roster script | `RosterChange` (§10.1) |

## 6. Processes

### 6.1 Roster change

Every roster write follows these steps. The roster script runs them once per gamertag, and `changeRoster` in the backlog `RosterAdmin` Lambda (P2.1) runs the same steps.

1. Take the actor from the caller's verified identity: the STS caller ARN of the roster script's account check (§4.2), or the function URL's `userArn` in `RosterAdmin`. Generate the request's `clientRequestId`, or take it from the validated body (§4.3).
2. Read `HEAD` with a consistent read, giving version `v`. Query the change items up to `v` with consistent reads and fold them (§5.1). A reader that caches a folded roster, such as a Lambda execution environment, queries only the items after its cached version and folds them onto it. Fail with `ROSTER_INTEGRITY` when the fold does not reach version `v` or its hash differs from `HEAD.rosterSha256`.
3. When a change in the log has the request's `clientRequestId`, report it as already recorded and write nothing.
4. Check the request against the roster at `v` with `checkChange` from `@mcc/roster` (§4.3), which also computes the key conflict and near-key warnings.
5. Build change `v + 1` and the new hash. In one `TransactWriteItems`, put the change item with `attribute_not_exists(sk)` and put the `HEAD` item with the condition `attribute_not_exists(sk)` when `v` is 0 or `rosterVersion = :v` otherwise.
6. When the transaction is cancelled by a failed condition, or its outcome is unknown after a transport error, return to step 2 with the same `clientRequestId`, at most 3 attempts in all. After 3 failed conditions the change is refused with `CONCURRENT_CHANGE`. After a transport error on the last attempt it fails as `UNAVAILABLE`.
7. Report the change with its `action`, `gamertagId`, `rosterVersion` and any near-key warning.

### 6.2 Roster read and resolution in `extract-text`

Spec 1.1 §7.1 gains one step and two step changes:

1. Unchanged. `manifest.json` records `rosterMatcherVersion`.
2. Unchanged.
3. Unchanged.
4. **New.** `rosterSource.read(namespace)` reads the roster as in §6.1 step 2 and fails with `RosterIntegrityError` on a hash mismatch. When this execution environment has not yet confirmed the version's snapshot, it writes the snapshot with `If-None-Match: *`. On `412` it reads the existing object and fails with `RosterSnapshotMismatchError` unless its `rosterSha256` matches.
5. Textract, as spec 1.1 step 4.
6. Sample row colours, run `processScoreboardImage` and normalize every block, as spec 1.1 step 5. Then call `resolvePlayers(rows, roster)` (§7), attach each row's `playerResolution`, and write normalized observations with the roster reference.
7. Write the completion with the roster reference and `playerMatchCounts`, append `RUN_SUCCEEDED`, log `Screenshot processed` with the three counts, and return `ExtractTextOutput` with the roster reference. Its rows carry no `playerResolution`.

`write-extracted-csv` reads `normalized/observations.json` from the `normalizedArtifact` it receives, checks that its `runId` and roster reference match the input, takes the rows with their `playerResolution` from `parser.rows`, writes them and the roster reference into `extracted-table.json`, and writes the CSV with §7.6. A run without resolutions, written before P3.2, renders as before with an empty `PlayerMatch`.

### 6.3 Replay

A replay (spec 1.1 §6.2) runs the same steps and reads the roster at its current version. The new run records that version beside the earlier run, which keeps its own. Comparing the two runs' `playerResolution` values shows what a roster change did.

### 6.4 Retries and failure

- The roster script relies on the AWS CLI's default retries for each call. When a transaction still fails with an unknown outcome, it returns to §6.1 step 2 with the same `clientRequestId`, so a change that committed before the response was lost is found in the log and not written again.
- In `extract-text`, DynamoDB throttling and server errors surface as `ThrottlingException`, `ProvisionedThroughputExceededException` or `InternalServerError`, which the workflow already retries (spec 1.1 §6.3). `RosterIntegrityError` and `RosterSnapshotMismatchError` are not retried. Each failure writes the `FAILED` completion and `RUN_FAILED` as spec 1.1 §7.1 describes. Textract has not been called.

## 7. Matching

`resolvePlayers(rows, roster)` in `@mcc/roster` is pure and deterministic. Its input is the parser's rows, whose `player` is the name tidied by spec 1.1 §8.2 step 4 (icon words dropped, one leading clan tag removed, whitespace collapsed), and the active entries of one roster version.

### 7.1 Matching key

`rosterKey(text)` applies these steps in order:

1. Unicode NFKC normalization.
2. Lowercase.
3. Remove every whitespace character.
4. Replace each `rn` with `m`, left to right, without overlap.
5. Replace each character in a look-alike group with the group's representative. Every other character is kept.

| Group | Representative |
| --- | --- |
| `i`, `l`, `1`, `\|` | `1` |
| `o`, `0` | `0` |
| `s`, `5` | `5` |
| `b`, `8` | `8` |

| Text | Key |
| --- | --- |
| `Player05`, `PIayer05`, `player05` | `p1ayer05` |
| `Player06`, `Player 06` | `p1ayer06` |
| `Player10 B C` | `p1ayer108c` |
| `Corn Dog` | `c0md0g` |

### 7.2 Distance

`keyDistance` is the Levenshtein distance between two keys over Unicode code points, with insertion, deletion and substitution each costing 1. Transpositions cost 2, because OCR reads characters in place and does not swap them. `textDistance` is the same distance between the name as read and the chosen gamertag, case-sensitive and without the key steps.

### 7.3 Per-row rule

For each row, with `asRead` the row's `player`:

1. When the roster has no active entry, or `asRead` has more than 32 characters, the row is `UNMATCHED` with `NO_CANDIDATE` and null distances. No gamertag is longer than 21 characters, so a longer reading is never a near match, and the cap bounds the work.
2. When an active entry's gamertag equals `asRead` exactly, the row is `EXACT` for that entry, with `keyDistance` and `textDistance` 0. Gamertags are unique ignoring case, so at most one entry matches.
3. Otherwise compute the key distance to every active entry. Let `d1` be the smallest. When no entry at `d1` is within its own budget, the row is `UNMATCHED` with `NO_CANDIDATE`, so a reading far from every entry is never called ambiguous.
4. When more than one entry is at `d1`, the row is `UNMATCHED` with `AMBIGUOUS`.
5. Let `A` be the one entry at `d1` and `d2` the smallest distance among the other entries (none when `A` is the only entry). When `d2` exists and is below `d1 + margin(d1)`, the row is `UNMATCHED` with `AMBIGUOUS`. Otherwise it is `RESOLVED` to `A`.

| Parameter | v1 value | Notes |
| --- | --- | --- |
| Budget of entry `A` | `min(2, floor(length of rosterKey(A) / 5))` | 0 edits for keys of 1 to 4 characters, 1 for 5 to 9, 2 for 10 or more. Measured on the roster entry, because a reading can have extra characters. |
| `margin(0)` | 1 | A key-equal reading resolves when no other entry is key-equal, which always holds because no two active entries share a key (§1). |
| `margin(d)` for `d >= 1` | 2 | A near reading resolves only when every other entry is at least two edits further away. |
| Longest reading considered | 32 characters | Rule 1. |

Every record carries `keyDistance` (`d1`, or 0 for `EXACT`) and `runnerUpDistance` (`d2`, or the smallest key distance to any other entry for `EXACT`), so the thresholds can be checked against recorded runs (§9).

### 7.4 One entry per game

After every row has a result from §7.3, for each entry chosen by more than one row:

- When any row is `EXACT` for the entry, every row `RESOLVED` to it becomes `UNMATCHED` with `ENTRY_CLAIMED`.
- Otherwise, when two or more rows are `RESOLVED` to it, all of them become `UNMATCHED` with `ENTRY_CLAIMED`.

Rows never move to their second-best entry. Two rows `EXACT` for the same entry both stay `EXACT`, and spec 2.1 `H001_DUPLICATE_PLAYER` flags the pair. The rule is order-independent, so the same rows in any order give the same results.

### 7.5 Error types

A `RESOLVED` row records `errorTypes` from spec 2.3's `CellErrorType` vocabulary (spec 2.3 §7.3), derived from a minimal Levenshtein alignment of `asRead` to the gamertag on the raw, case-sensitive text. The alignment is traced back from the end, preferring a match or substitution, then a deletion from `asRead`, then an insertion, so it is unique.

| Alignment step | Error type |
| --- | --- |
| A substitution, including a case-only change | `GLYPH_SUBSTITUTION` |
| A character of `asRead` deleted | `EXTRA_CHARACTERS` |
| A character of the gamertag inserted | `MISSING_CHARACTERS` |

Types are sorted and unique, as spec 2.3 requires. `EXACT` and `UNMATCHED` rows have none. `PIayer05` resolved to `Player05` records `GLYPH_SUBSTITUTION`, and `Player 06` resolved to `Player06` records `EXTRA_CHARACTERS`. A reviewer correcting either cell in spec 2.3 would choose the same type.

### 7.6 CSV rendering

`rowsToCsv(rows)` writes the header `Team,Player,Score,Kills,Assists,Deaths,Win,Loss,PlayerMatch` and quotes every value as spec 1.1 §8.6 does.

| `playerResolution.status` | `Player` | `PlayerMatch` |
| --- | --- | --- |
| `EXACT` | the gamertag, equal to the name as read | `EXACT` |
| `RESOLVED` | the roster gamertag | `RESOLVED` |
| `UNMATCHED` | the name as read | `UNMATCHED` |
| no `playerResolution` | the name as read | empty |

The CSV carries neither the name as read for `RESOLVED` rows nor `reviewFlags`. `extracted-table.json` carries both.

## 8. Relationship with #161, spec 2.1 and spec 2.3

### 8.1 Division of work with #161

Issue #161 adds `reviewFlags` to `CsvRow`: `LOW_WORD_CONFIDENCE` when a player-name `WORD` scores below 50, and `SPLIT_TRAILING_DIGITS` when trailing digits are split into their own word and either word scores below 90. Flags never change the name or the CSV header, which this spec defines (§7.6).

| Concern | Covered by |
| --- | --- |
| Marking a reading Textract may have misread, from its `WORD` confidences, with or without a roster | #161 (`reviewFlags`) |
| Naming the player when the reading matches a roster gamertag | this spec (`playerResolution`) |
| Keeping the name as read in parser rows, normalized observations and the export | both; neither changes it |
| The CSV header and `Player` column | this spec (§7.6) |
| Readings of players who are not on the roster | #161 flags them when confidence is low; this spec marks them `UNMATCHED` |
| Delivery | #161 delivers `reviewFlags`; the slices in §20 deliver this spec |

The two stages are independent. `resolvePlayers` does not read `reviewFlags`, and the flag rules do not read the roster. A row can be flagged and resolved: in capture 2, `PIayer05` and `Player 06` carry #161's flags and are `RESOLVED` here. A `RESOLVED` row keeps its flags, because they describe the reading, which is unchanged. Requiring a flag before a near match may resolve is backlog P5.3, to be taken up if §9 finds unknown players resolved to known gamertags.

### 8.2 Spec 2.1

- **Player normalization.** `H001_DUPLICATE_PLAYER` compares names after tag removal, whitespace collapse and case folding (spec 2.1 §7.3). `rosterKey` starts from the tidied name, which already has its tag removed, folds case the same way, removes whitespace instead of collapsing it, and adds the look-alike groups. For ASCII names, which every gamertag is, two names `H001` treats as equal always share a roster key; names that share a key need not be equal under `H001`. `H001` keeps its own rule.
- **Look-alike tables.** Spec 2.1 `C001_SUSPICIOUS_GLYPH` maps letters to digits in integer cells only (spec 2.1 §7.2). The roster's groups are symmetric classes for names, deliberately smaller, and neither replaces the other.
- **Name pattern.** Roster entries must match spec 2.1's default `playerNamePattern` (§4.3). A later change to spec 2.1's pattern does not change the roster's validation; the two are separate constants.
- **Inputs to scoring.** Spec 2.1 reads `observedText` and `parser.rows`, and `parser.rows[].player` stays as read, so spec 2.1 v1 is unaffected. Resolution fields are not features in `features-v1`. Adding them is a spec 2.1 decision under a new `featureSchemaVersion` (P5.6).

### 8.3 Spec 2.3

- **Shared vocabulary.** A resolution records the misread it undid with spec 2.3's `CellErrorType` (§7.5), and one cell's resolution and adjudication describe the same thing: the text as read (`asRead`, or the cell's `observedTextAtReview`) and the text it should be (`gamertag`, or the resolved text).
- **Join.** A resolution belongs to row `i` of `parser.rows`. Spec 2.1 P0.3's `parser.provenance` gives that row's table row (`rowIndexes[i]`) and the `PLAYER` column (`fieldColumns.PLAYER`), which identify the player cell's `cellObservationId`, the key of its spec 2.3 cell adjudication.
- **Agreement.** A label's resolved text, tidied with spec 1.1 §8.2 step 4, agrees with an `EXACT` or `RESOLVED` resolution when it equals the gamertag. An `UNMATCHED` row is a missed resolution when its tidied label equals the gamertag of an entry in the run's roster snapshot. Cells resolved `UNREADABLE` or `SKIPPED` have no label. P5.1 measures the matcher this way.
- **Independence.** A resolution is not an adjudication. It is never written under `adjudications/`, never sets a `ValueSource`, and is not shown to reviewers in v1, because spec 2.3's evidence panel shows observed text and parser output only (spec 2.3 §9.1). Labels therefore measure the matcher instead of echoing it, and blind labels stay blind. Showing roster suggestions to reviewers would be a spec 2.3 change that records when a suggestion was shown, like `priorityShown` (P5.7).
- **Validated tables.** The validated table's `player` comes from the reviewed cell (spec 2.3 §8.4), so the roster plays no part in it. #159 can link validated names to roster entries by gamertag.

## 9. Matching evidence

### 9.1 The #91 fixtures

`halo3-two-team-capture-1` and `halo3-two-team-capture-2` hold 16 player rows of 14 distinct placeholder gamertags. Capture 1 reads all 8 names exactly. Capture 2 reads 6 exactly and misreads 2. The 14 placeholders have 14 distinct keys, so the roster would accept all of them (§4.3). With a test roster of the 14 placeholders, the v1 rule gives:

| Capture | Rows | Expected results |
| --- | --- | --- |
| 1 | 8 | 8 `EXACT` |
| 2 | 8 | 6 `EXACT`; `PIayer05` `RESOLVED` to `Player05` with `keyDistance` 0, `runnerUpDistance` 1, `textDistance` 1, `GLYPH_SUBSTITUTION`; `Player 06` `RESOLVED` to `Player06` with `keyDistance` 0, `runnerUpDistance` 1, `textDistance` 1, `EXTRA_CHARACTERS` |

Placeholders are much closer to each other than real gamertags are: `Player05` and `Player06` are one edit apart. Both resolutions therefore pass the key-equal margin with nothing to spare, and a key-equal margin of 2 would refuse them. The same closeness makes every near reading of a placeholder ambiguous. With `Player05` removed from the test roster, `PIayer05` is one edit from `Player06`, `Player08` and others, and becomes `UNMATCHED` with `AMBIGUOUS`. So the fixtures test key-equal resolution and the ambiguity refusal. They cannot test the edit budgets, which need synthetic cases (§16.1) and real names (§9.3).

### 9.2 The #161 misreads

Both misreads are differences the key removes: a look-alike substitution (`l` read as `I`, `WORD` confidence 39) and a space inserted before trailing digits (`WORD` confidences 55 and 88). Neither needs an edit after the key. No capture yet shows a misread that does, such as a dropped character or a substitution outside the §7.1 groups, so the budgets and the near-match margin in §7.3 are initial values without evidence behind them.

### 9.3 Further captures

P4.1 adds `applications/match-to-csv/scripts/evaluate-roster.ts`:

```text
npx tsx scripts/evaluate-roster.ts --environment <dev|prod> [--ephemeral <name>] [--roster-version <n>] --captures <dir> --truth <file>
```

- **Roster.** The script reads the roster from AWS, never from a file. It runs the same account check as the roster script (`scripts/account-guard.mjs`, §4.2), finds `RosterFunctionUrl` the same way, and pages through `GET /v1/changes` with a SigV4 request signed by the operator's credentials, through `scripts/lib/roster-api.mjs`, which P2.3 adds for the CLI. It folds changes 1 to `--roster-version`, or to the latest version when the flag is absent, with `foldRoster` (§5.1), and stops with exit status 2 when the fold's hash differs from that change's `rosterSha256`. The roster stays in memory for one run. The script never writes it, or anything else, to disk, and needs no permission beyond the operator's (§13.4).
- **Captures and truth.** `--captures` is a directory of capture files from `scripts/capture-textract.ts`, the Textract responses the capture scripts already keep outside the repository. `--truth` is a JSON file that gives, for each row of each capture, the `gamertagId` of the roster entry the row shows, taken from `roster list`, or `null` when the player is not on the roster. It holds IDs only, never a gamertag. The script exits 2 when a value is neither `null` nor an `evidenceId()` (spec 1.1 §5.1), or names no entry in the folded roster; an entry inactive at that version counts as not on the roster. Whether a reading is a misread is decided by comparing it with the entry's gamertag from the roster read from AWS. The script refuses both paths when they are inside a Git working tree, as the capture scripts do.

It runs the parser and `resolvePlayers` and prints the roster version and hash it used, then counts and distance histograms, never a name:

- rows by status and reason;
- wrong resolutions: `EXACT` or `RESOLVED` to an entry other than the truth, including any entry when the truth is `null`;
- missed resolutions: `UNMATCHED` rows whose truth is on the roster, by `keyDistance`;
- `runnerUpDistance` of correct resolutions, and `keyDistance` of readings whose truth is not on the roster.

The thresholds are checked on at least 30 screenshots from at least 5 sessions, about 240 rows, including players who are not on the roster. They are kept when that sample has no wrong resolution and resolves at least 90% of misread names whose truth is on the roster. A wrong resolution means tightening the budget or the margin. Missed resolutions within reach of the budget, with no wrong resolution, support loosening it. Either change is a new `rosterMatcherVersion` filed as its own issue; earlier runs keep their version, and a replay applies the new one. P4.2 records the first check's counts on its issue.

### 9.4 Spec 2.3 labels

Once spec 2.3 writes adjudications, every reviewed run measures the matcher against reviewer decisions (§8.3), including how often unknown players' readings fall within the budget of a roster gamertag. P5.1 reports those counts and replaces the P4.1 evaluation sample as the evidence for later threshold changes.

### 10.1 Shared contracts

```typescript
type CellErrorType =                     // spec 2.3 §7.3; defined once (§8.4)
  | 'GLYPH_SUBSTITUTION' | 'MISSING_CHARACTERS' | 'EXTRA_CHARACTERS'
  | 'SHIFTED_CELL' | 'MERGED_CELL' | 'OTHER';

type RosterChangeAction = 'ADD' | 'DEACTIVATE' | 'REACTIVATE';

interface RosterChange {
  schemaVersion: 'roster-change/v1';

  rosterVersion: number;                 // 1-based, no gaps
  action: RosterChangeAction;
  gamertagId: string;                    // evidenceId(), assigned by ADD
  gamertag: string;                      // validated display text (§4.3)
  reason: string | null;                 // at most 256 characters
  actorArn: string;                      // the writer's IAM ARN: the STS caller of the roster script
  clientRequestId: string;
  changedAt: string;
  rosterSha256: string;                  // roster hash after this change (§5.1)
}

interface RosterEntry { gamertagId: string; gamertag: string }

interface RosterSnapshot {
  schemaVersion: 'roster-snapshot/v1';
  namespace: string;
  rosterVersion: number;
  rosterSha256: string;
  entries: readonly RosterEntry[];       // active entries, sorted by gamertagId
}

interface RosterReference {
  namespace: string;
  rosterVersion: number;
  rosterSha256: string;
  snapshot: S3ObjectReference;
}

type PlayerMatchStatus = 'EXACT' | 'RESOLVED' | 'UNMATCHED';
type UnmatchedReason = 'NO_CANDIDATE' | 'AMBIGUOUS' | 'ENTRY_CLAIMED';

interface PlayerResolution {
  status: PlayerMatchStatus;
  asRead: string;                        // CsvRow.player, the tidied name as read
  gamertagId: string | null;             // null when UNMATCHED
  gamertag: string | null;               // null when UNMATCHED
  keyDistance: number | null;            // d1; 0 for EXACT; null when no entry was compared
  runnerUpDistance: number | null;       // d2; null when no other entry exists
  textDistance: number | null;           // asRead to gamertag; null when UNMATCHED
  errorTypes: readonly CellErrorType[];  // RESOLVED only, sorted
  unmatchedReason: UnmatchedReason | null;
}

interface CsvRow {
  team: string; player: string; score: string; kills: string;
  assists: string; deaths: string; win: number; loss: number;
  reviewFlags?: RowReviewFlag[];         // #161
  playerResolution?: PlayerResolution;   // in normalized observations and the export from P3.2 on
}

interface ExtractTextOutput {
  runId: string;
  source: SourceScreenshot;
  rows: CsvRow[];
  normalizedArtifact: S3ObjectReference;
  roster?: RosterReference;              // present on runs from P3.1 on
}                                        // rows never carry playerResolution (§1)

// Roster API bodies (§4.1)
interface AddGamertagRequest { gamertag: string; reason?: string; clientRequestId: string }
interface ChangeGamertagStatusRequest { reason?: string; clientRequestId: string }
interface RosterChangeResponse {
  change: RosterChange;
  entry: RosterEntry & { status: 'ACTIVE' | 'INACTIVE' };
  rosterVersion: number;
  rosterSha256: string;
  warnings: { nearKeyGamertags: readonly string[] };
}
```

Change requests are validated by `checkChange` (§4.3) before any write, in the roster script and in the backlog `roster-admin`. `asRead` is copied from parser output and never interpreted beyond §7; matching ignores readings over 32 characters.

### 13.4 Permissions

| Principal | Roster table | KMS data key | Evidence bucket |
| --- | --- | --- | --- |
| Administrators running the roster script (`mcc-<env>-admin`) | `GetItem`, `Query` and `PutItem`; the §6.1 transaction holds two puts, so the script needs only `PutItem` to write | use through DynamoDB | none |
| `ExtractText` | `GetItem` and `Query`, with `dynamodb:LeadingKeys` equal to `ROSTER#<namespace>` | the existing encrypt and decrypt grant, which covers DynamoDB | the existing `GetObject` and `PutObject`, which cover snapshots |
| `WriteExtractedCsv` | none | the existing grant | adds `GetObject` on `<ns>submissions/*/runs/*/normalized/observations.json` |
| `RosterAdmin` (backlog, P2.1) | `GetItem`, `Query` and `PutItem`, with `dynamodb:LeadingKeys` equal to `ROSTER#<namespace>` | decrypt, encrypt and generate data keys through DynamoDB (`kms:ViaService`) | none |
| Operators (backlog, P2.2) | none | none | none; they invoke `RosterAdmin` only through its function URL, under the operator policy below |

The administrator profiles already allow every action the roster script uses, so no policy is added for it. Their rights are not confined to one partition. The script itself writes only the partition its options name (§4.2). Until the admin API or screen exists, only administrators change the roster. No application role has `UpdateItem`, `DeleteItem`, `BatchWriteItem` or any table-management action on the roster table. Ephemeral roles carry the local boundary and `/mcc-local/` path. The local execution role's existing `ManageEphemeralCompute` statement (`lambda:*` on `<app>-e-*` functions) already covers creating and deleting function URLs. P1.2 lets the local workload boundary allow the roster actions above only when the leading key is `ROSTER#ephemeral/${aws:PrincipalTag/Ephemeral}`, so an ephemeral stack can never read or write the stable roster.

**Operator policy (backlog, P2.2).** Lambda authorizes a request to a function URL with `AuthType: AWS_IAM` only when the signed caller is allowed both `lambda:InvokeFunctionUrl` and `lambda:InvokeFunction` on the function ([function URL access control](https://docs.aws.amazon.com/lambda/latest/dg/urls-auth.html)). The admin stack adds no resource-based policy to `RosterAdmin`, so the caller's identity-based policy in the same account is the only grant. The operator policy is the minimum the signed CLI and the evaluation script (§9.3) need:

| Statement | Action | Resource | Condition |
| --- | --- | --- | --- |
| `InvokeRosterFunctionUrl` | `lambda:InvokeFunctionUrl` | `function:admin-*-RosterAdmin` | `StringEquals` `lambda:FunctionUrlAuthType` = `AWS_IAM` |
| `InvokeRosterThroughFunctionUrl` | `lambda:InvokeFunction` | `function:admin-*-RosterAdmin` | `Bool` `lambda:InvokedViaFunctionUrl` = `true` |
| `ReadRosterFunctionUrl` | `cloudformation:DescribeStacks` | `stack/admin-*/*` | none |

Resources are in the operator's account and Region. `admin-*-RosterAdmin` matches the stable functions (`admin-dev-RosterAdmin`, `admin-prod-RosterAdmin`) and ephemeral ones (`admin-e-<name>-RosterAdmin`) and no other function. The condition on `lambda:InvokeFunction` keeps the recorded actor trustworthy. A direct `Invoke` lets the caller send any event, including a `requestContext.authorizer.iam.userArn` that names someone else, and the handler cannot tell that event from one the function URL built. Under the condition, an operator's only way in is a signed function URL request, for which Lambda supplies the caller. The policy has no DynamoDB, KMS or S3 action.

P2.2 commits the policy as `docs/self-hosting/policies/roster-operator.json.template`, with `ACCOUNT_ID` and `AWS_REGION` placeholders like the existing local deployer template, and documents granting it. The `mcc-<env>-admin` administrator profiles already allow every action in it; a role for people who only maintain the roster, such as an IAM Identity Center permission set, gets exactly this policy. §18.13 covers administrators, whose wider rights bypass it.

### 13.5 Deployment

P1.1 is applied in dev and prod before P3.1 merges, and in an environment before the roster script writes there. The `match-to-csv` stack deploys through `scripts/cdk-app.mjs` as today. The deploy preflight lives in `.github/workflows/_delivery-deploy-environment.yml`, and the `match-to-csv` preflight fails when `/mcc/<env>/roster/table-name` is missing. The roster script deploys nothing. An administrator loads the first roster with its `add` command. Until then every run is `UNMATCHED`, which changes nothing a player sees except the new column. When P2.2 lands, the `admin` preflight checks the same parameter, and post-deploy verification checks that `RosterFunctionUrl` answers an unsigned request with `403`.

## 14. Security and privacy

1. Roster contents never enter the repository. No roster file is committed. Tests use the placeholder names of the #91 fixtures and synthetic names. The roster script takes gamertags only as arguments. The evaluation script reads the roster from AWS, takes truth as roster IDs rather than gamertags, refuses capture and truth paths inside a Git working tree, and prints only counts.
2. Roster contents live only in AWS under the application data key: change items in the roster table, which DynamoDB encrypts with the foundation data key, including its point-in-time backups; snapshots, resolutions and CSVs in the evidence bucket, encrypted with the same key. No roster file exists outside AWS. The roster script reads the table, and the evaluation script reads through the roster API; each holds the roster in memory for one command. The roster script prints it only to the terminal, and neither writes it to disk (§4.2, §9.3).
3. Lambda logs never contain gamertags, readings or `actorArn`, which can hold a session name such as an email address. `extract-text` logs match counts only, and `RosterAdmin`, when P2.1 lands, logs `action`, `gamertagId`, `rosterVersion`, status codes and `requestId`. The roster script writes no log. It prints to the administrator's terminal only. Step Functions execution data carries names as read, as spec 1.1 §18.9 records, but never a roster gamertag, because `ExtractTextOutput` rows carry no resolution (§1).
4. The roster script runs the account check of `scripts/cdk-app.mjs` before any other AWS call, and makes every call with the credentials it checked. It takes the actor from STS, never from an argument, so a change record names the identity that wrote it.
5. The roster script is the only writer, and only administrators run it. It validates every change and applies the conflict check before it writes. The table cannot enforce that, because an administrator can write the table without the script (§18.13). Until the admin API or screen exists, no one else may change the roster, and no operator policy grants table access.
6. Stack namespaces come from the deployment, never from a request, and IAM `LeadingKeys` conditions confine every stack role to its own partition. The roster script writes `ROSTER#stable`, or with `--ephemeral <name>`, which only dev accepts, `ROSTER#ephemeral/<name>`.
7. Gamertags and readings are untrusted text. They are validated (§4.3) or length-capped (§7.3) before matching, used only as data, and never as keys or paths except through validated IDs.

## 15. Observability

- The roster script prints each change it writes, or the refusal, to the administrator's terminal. When P2.1 lands, `RosterAdmin` writes one JSON log line per request with the fields in §14 item 3, and `Roster changed` per committed change.
- `extract-text` adds `exact`, `resolved` and `unmatched` counts to its `Screenshot processed` line and to `completion.json` metrics. When spec 1.3's stage event exists, P3.2 adds the same three counts to it.
- The audit record for "who changed the roster" is its change log (`npm run roster -- history`). The audit record for "why does this CSV name this player" is the run's `playerResolution` and roster snapshot.

## 18. Risks and accepted limitations

1. **Unknown players near a roster gamertag are resolved to it.** A player who is not on the roster and whose name is within the budget of exactly one roster gamertag, with no other entry within the margin, appears in the CSV under that gamertag, marked `RESOLVED`. The budgets and margin (§7.3) limit this, the status column shows it, and spec 2.3 reviews every cell, so validated tables never carry it. §9.3 measures it, and P5.3 can require a #161 flag for near matches.
2. **The thresholds have no near-match evidence.** Both observed misreads are key-equal (§9.2). The budgets and margin are initial values, checked by P4.2 and P5.1.
3. **Placeholder fixtures are closer than real names.** They exercise key-equal resolution and ambiguity only (§9.1). Real-name checks happen outside the repository.
4. **Folding merges some real names.** Lowercase `i` and `l`, `rn` and `m`, and the other groups can give two real gamertags one key. The roster refuses the second, with no override (§1), so at most one of them is on the roster. Every reading of the other player's name that shares the key, including a correct one, resolves to the gamertag on the roster and is marked `RESOLVED`. The operator can leave both off the roster instead, and then both pass through as `UNMATCHED`. Accepted because #163 requires the refusal; the `PlayerMatch` column shows the resolution, and spec 2.3 reviews every cell, so validated tables never carry it.
5. **The roster lags the league.** A new player is `UNMATCHED` until someone adds them, and a renamed player is unmatched or matched under the old gamertag until someone changes the roster. Runs are not re-resolved except by replay.
6. **Replay calls Textract again.** Applying a newer roster to an old run costs a provider call and creates a full new run. P5.4 adds re-resolution without Textract.
7. **Roster history cannot be erased.** The change log is append-only, and snapshots sit under Object Lock. A player who asks to be removed can be deactivated, but their gamertag stays in the log, the snapshots and every screenshot already stored. P5.5 covers erasure on request.
8. **Every run depends on the roster table.** When it is unavailable past the workflow's retries, runs fail before Textract and can be replayed. Accepted because DynamoDB on-demand with point-in-time recovery is more available than Textract, which every run already needs.
9. **`write-extracted-csv` reads normalized observations.** Keeping roster gamertags out of workflow state (§1) costs one extra `GetObject` per run and a read permission on normalized observations for the export stage. Names as read still reach Step Functions logs, as spec 1.1 §18.9 records.
10. **Ephemeral roster partitions never expire.** They are a few items each. P5.8 adds cleanup.
11. **Snapshots exist only for versions a run used.** A version no run read has only its change items, from which it can still be rebuilt.
12. **The function URL will be reachable from the internet (backlog, P2.2).** Lambda rejects any request without a valid SigV4 signature from a principal allowed both `lambda:InvokeFunctionUrl` and `lambda:InvokeFunction` on the function (§13.4), before the function runs. Accepted because the URL is not secret and needs no further protection; a person with invoke rights can already change the roster through the signed CLI.
13. **Validation runs on the administrator's machine.** The roster script validates every change and applies the conflict check, but the table accepts any write its caller is allowed to make. An administrator, or any role with DynamoDB write access to the table, could write change items without the script, with a forged actor or a change the checks would refuse. A write that breaks the fold still fails the next read with `ROSTER_INTEGRITY` (§6.1, §6.2), but a consistent one does not. Accepted because administrators can already change every resource in the account, and only administrators change the roster until the admin API or screen exists. When P2.2 lands, people who only maintain the roster get the operator policy (§13.4), which has no table access.

## 20. Delivery plan: phases and slices

This section is the backlog source for building the component. It is written to be turned directly into GitHub issues.

### 20.1 How to file this plan

- Each **phase** becomes one epic, titled with the phase title, with its goal and exit criteria as the body. Create epics only when someone explicitly asks for filing.
- Each **slice** becomes one leaf issue under its phase epic, titled without its code, with `Plan ID: P<n>.<m>` in the body. File with `/ac-create-github-issue`.
- **Size** is XS, S or M. Split a slice by independently testable behavior when it outgrows one reviewable PR; the original Plan ID becomes the container.
- **Blocked by** lists Plan IDs. "Spec 2.3 P<n>.<m>" names a slice of [spec 2.3](2.3-cell-labeling.md), and `#161` names the review-flags issue. Create native blocked-by links after every issue in the batch exists. Blockers in earlier phases still apply.
- **Acceptance** bullets become the issue's acceptance criteria verbatim. Every slice also inherits §20.3.
- **Spec** lists the sections the implementer must read. Link them; this document stays the source of truth.
- Plan IDs are stable. Deferred slices keep their IDs and move to the backlog phase; new slices take the next free number in their phase.
- Phase 5 is backlog.

### 20.3 Definition of done for every slice

- Handlers keep I/O behind an injected dependencies object; only default dependencies construct SDK clients. `@mcc/roster` stays pure.
- New behavior has tests that run without AWS in the workspace's test runner (§16.1), and each workspace stays above its coverage thresholds.
- `npm run check` passes. Slices that touch CDK also pass `npm run app:synth -- <app> --environment dev`, and for `match-to-csv` `npm run verify:bundle --workspace @mcc/match-to-csv`. Slices that touch `infrastructure/` pass `npm run tofu:check`.
- Any change to matching behavior bumps `rosterMatcherVersion` (§5.5).
- No real gamertag, domain, address or account ID appears in code, fixtures, logs or docs.
- Operator-visible changes update `applications/admin/TESTING.md`, `applications/match-to-csv/README.md`, `docs/self-hosting/` or spec 1.1 in the same PR.

### 20.4 Dependency order and parallel lanes

P0.1, P1.1 and P1.2 start together. P0.2 follows P0.1. The roster script (P2.4) and the match-to-csv lane (P3.1 -> P3.2 -> P3.3) run in parallel once P0.2 merges and P1.1 is merged. P3.1 waits for P1.1 to be applied in both environments. The critical path is P0.1 -> P0.2 -> P3.1 -> P3.2 -> P3.3. Phase 4 waits for the backlog slices P2.1 to P2.3, because P4.1 reads the roster through the roster API. The first real feedback is P3.3 in dev with a roster loaded through P2.4, when live CSVs start naming players from the roster.
