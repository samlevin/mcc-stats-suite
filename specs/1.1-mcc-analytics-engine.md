# Match-to-CSV: Technical Specification

**Status:** Specification for v1 delivery

**Version:** 2.0-draft

**Date:** October 14, 2026

**Component:** `applications/match-to-csv`, with shared code in `packages/contracts` and `packages/cdk-config` and persistent resources in `infrastructure/modules/foundation`

**Runtime:** TypeScript, Node.js 22 on AWS Lambda (ARM64), orchestrated by AWS Step Functions

**Deployment:** one AWS CDK stack per stable environment (`dev`, `prod`) from GitHub Actions, plus ephemeral developer stacks in the dev account

**OCR provider:** Amazon Textract `AnalyzeDocument` with the `TABLES` feature

**Persistent state:** an immutable S3 evidence bucket and a raw-email bucket, both owned by the OpenTofu foundation; `extract-text` also reads the foundation's gamertag roster table ([spec 1.2](1.2-gamertag-roster.md))

**External dependencies at runtime:** Amazon SES, S3, EventBridge, Step Functions, Lambda, Textract, DynamoDB, KMS, SSM Parameter Store and SQS

**Out of scope:** match records, screenshot-to-match association, OCR adjudication, anomaly scoring, model training, public user interfaces

Halo: The Master Chief Collection (MCC) players email post-game scoreboard screenshots to a fixed address. This component turns each screenshot into OCR evidence and a per-screenshot CSV of player statistics. Once every screenshot of an email succeeds, it also writes one CSV per roster gamertag in the legacy spreadsheet's format. It keeps every input and every provider response so later features can replay, compare, label and train on them without asking players to resend anything.

## 1. Resolved requirement decisions

Each row records how a requirement is resolved. These are product decisions.

| Requirement | Decision | Reason |
| --- | --- | --- |
| Preprocess each image: EXIF auto-rotation, landscape enforcement, sharpening, Rekognition `DetectText` crop with full-image fallback | No preprocessing. Textract receives the stored original bytes after an integrity check. The run manifest records `preprocessingVersion: none-v1`. | Textract is built for unprocessed images, and sharpening or resizing can add artifacts that lower accuracy. Sending the original keeps every provider coordinate aligned with the stored evidence, which row-colour sampling and later labeling depend on. A crop would need its own stored artifact, failure modes and tests. |
| Debug mode writes a cropped PNG to `matches/<matchId>/cropped/` and logs crop dimensions | No debug mode. Every run writes its complete evidence (§5), so there is no debug flag. | With no crop there is nothing to debug. Full evidence on every run is more useful than an opt-in partial record. |
| One CSV per match | One CSV per processing run, which is one per screenshot attempt. Each emailed submission also gets one CSV per roster gamertag, in the legacy spreadsheet's format (§8.6.1). | The system has no match entity. Grouping screenshots into matches belongs to the match-entry and association features. One email can carry screenshots of different matches. |
| CSV written to a dedicated output bucket | The CSV and its structured table are written under the run in the evidence bucket (`export/extracted.csv`, `export/extracted-table.json`). | The CSV is derived evidence and belongs next to the observations it came from. The foundation provisions an output bucket and an attachments bucket for later features; v1 writes to neither. |
| CDK provisions the raw-email, attachments and output buckets, the SES receipt rule set and the IAM policies | OpenTofu (`infrastructure/modules/foundation`) owns every persistent resource: the KMS key, all buckets, the receipt rule set, its activation, the shared `<alias>@<domain>` rule and the SSM parameters. CDK owns compute: Lambda functions, state machines, the EventBridge rule, the dead-letter queue, log groups and IAM roles. | Data must outlive application stacks, and no resource may be managed by two tools. The one exception is the ephemeral `<alias>+<name>@<domain>` receipt rule, which an ephemeral stack adds to the foundation rule set and removes with itself. |
| Architecture: SES -> S3 -> handler Lambda -> preprocess Lambda -> CSV | SES -> raw-email bucket -> EventBridge `Object Created` -> Step Functions Standard workflow -> intake Lambda -> `Map` over screenshots -> extraction Lambda -> export Lambda, then the per-gamertag export Lambda once every screenshot succeeded. | A state machine gives per-screenshot isolation, bounded concurrency, declared retries, an execution history and a replay entry point. |
| Emails must contain one or more image attachments | A message with no processable screenshot completes intake with status `REJECTED`, writes its evidence, and ends its execution as succeeded at the **Submission rejected** state (§6.1). | The `REJECTED` completion and `SUBMISSION_REJECTED` event record every rejected submission, so none is lost silently. A failed execution and its alarms then mean something broke, not that a sender made a mistake ([spec 1.3 §1](1.3-match-to-csv-observability.md#1-resolved-requirement-decisions)). |
| Non-image attachments are ignored | Non-image attachments are recorded as `NOT_AN_IMAGE` rejections and stay only in the retained raw MIME message. Rejected images are stored with their rejection codes. | The submission record explains every attachment. |
| Detect the header row dynamically, fall back to column order | The first row of the selected table is the header. Recognized labels map to fields. Any field left unmapped falls back to its standard position. | A fixed header row is deterministic, and the positional fallback still maps a field whose label Textract misreads. |
| Team detection by row background colour, MCC colour names, FFA when one cluster | Only two-team boards are supported, and free-for-all and three-team matches are not. A board whose player rows form one colour cluster, carry no colour, or form three or more clusters produces no rows, and the run succeeds and records why (§8.4). When both clusters get the same colour name, the second gets a numeric suffix (`Red 2`). | An unsupported board succeeds with no rows instead of failing, because the attachment `Map` tolerates no failed item (§6.1), so one failed screenshot would fail every other screenshot in the email. Names stay unique per screenshot, so win/loss assignment never merges the two teams. |
| Win/loss from the top player row | The top player row decides win and loss on two-team boards (§8.5). | MCC lists the winning player or team first. |
| JSON logs with `ERROR`, `WARN`, `INFO`, `DEBUG`, `TRACE` | Each line is one JSON object with `level`, `message` and context fields, written to standard output. | CloudWatch Logs indexes JSON fields. |
| TAP unit tests for `processScoreboardImage` | Tests cover `processScoreboardImage`, every handler, the normalizer, CSV escaping, comparison, materialization, deployment configuration, bundling and receipt rules, with coverage thresholds that fail the test command (§16). | The parser is only one of several places where a regression loses evidence. |
| All buckets block public access and use encryption | Every bucket blocks public access and is encrypted. The raw-email bucket uses SSE-S3. Every other bucket uses SSE-KMS with the foundation key and S3 Bucket Keys. | SES writes the raw message, and SSE-S3 needs no key grant to the SES service principal. Application data uses a customer-managed key. |
| SES has explicit `PutObject` permission | The raw-email bucket policy allows `ses.amazonaws.com` to put objects only under `incoming/`, only from this account and only from a receipt rule set in this account. It denies every request without TLS. | Limits the service grant to the prefix SES needs. |
| Least-privilege Lambda IAM | Each function receives only the S3, KMS, Textract and SES actions it uses (§13.4), inside a permissions boundary. | Textract `AnalyzeDocument` has no resource-level permissions, so it is granted on `*` to the extraction function only. |

**Additional capabilities included:** append-only submission and run events, immutable writes enforced by S3 conditional requests, source hash verification before OCR, versioned pipeline stages recorded in every run, replay of a stored screenshot as a new run, cell-level comparison of two runs, deterministic training-data splits, ephemeral per-developer stacks with their own email address and object namespace, pre-deployment checks of SES and DNS, and post-deployment health checks.

## 2. Goals and non-goals

### 2.1 Goals

1. Accept scoreboard screenshots by email with no client software, account or upload page.
2. Preserve every input and every provider output immutably, so any result can be traced to the bytes and code versions that produced it.
3. Produce a quoted CSV of `Team,Player,Score,Kills,Assists,Deaths,Win,Loss,PlayerMatch` for each two-team screenshot, with any number of players on each team. Other boards produce no rows and a recorded reason (§8.4).
4. For each emailed submission, write one headerless `Date,Kills,Assists,Deaths,Win,Loss` CSV per roster gamertag with a matched row, ready to paste into that player's legacy spreadsheet (§8.6.1), and email those files to the CSV recipient list (§8.6.2).
5. Record each OCR cell with its geometry, confidence, semantic field and deterministic validation result, ready for human review.
6. Re-run extraction on stored evidence without changing earlier runs, and compare any two runs cell by cell.
7. Materialize unlabeled training datasets with splits that never leak a screenshot across partitions.
8. Let each developer deploy an isolated copy in the dev account that cannot touch shared stacks or shared evidence.

### 2.2 Non-goals

- Image preprocessing of any kind before OCR.
- Creating matches, associating screenshots with matches, or deduplicating screenshots of the same match.
- Correcting OCR text. Unknown layouts stay `UNKNOWN`, and suspicious values are flagged, never changed. The CSV's `Player` column (§8.6) and the per-gamertag files (§8.6.1) name the roster gamertag a player name resolved to. Every other artifact keeps the name as read.
- Adjudication, labeling, anomaly detection or model inference. Specs 2.1 and 2.3 cover those, reading the evidence this component writes.
- Authenticating senders beyond SES spam and virus scanning.
- Public access to any artifact, or any user interface.
- Exactly-once processing. Retries can produce extra submissions or runs; evidence is never overwritten (§18).

## 3. Runtime architecture

```text
Sender
  |
  v
Amazon SES inbound (foundation receipt rule set mcc-inbound-<env>)
  |  <alias>@<domain>           -> incoming/<env>/      (foundation rule)
  |  <alias>+<name>@<domain>    -> incoming/<name>/     (ephemeral stack rule)
  v
Raw-email bucket (SSE-S3, EventBridge notifications, 90-day expiry)
  |
  v
EventBridge rule: Object Created under incoming/<route>/  --(failed delivery)--> SQS DLQ
  |
  v
Step Functions Standard workflow <stack>
  |
  +-- Process email and attachments   (ProcessEmail Lambda)
  |     parse MIME, validate attachments, store originals and metadata,
  |     write ingestion, completion and events
  |
  +-- Rejected? (Choice on $.status)  REJECTED -> Succeed "Submission rejected"
  |
  +-- Process attachments (Map, max concurrency 2, one item per accepted screenshot)
  |     |
  |     +-- Extract text             (ExtractText Lambda)
  |     |     verify hash, read the roster, record request, call Textract, sample row colours,
  |     |     parse scoreboard, normalize observations, write completion and events
  |     |
  |     +-- Write extracted CSV      (WriteExtractedCsv Lambda)
  |           read the run's normalized observations,
  |           write extracted.csv and extracted-table.json under the run
  |
  +-- Write gamertag CSVs           (WriteGamertagCsvs Lambda, only after every item succeeded)
  |     read each run's extracted-table.json,
  |     write one CSV per roster gamertag under the submission
  |
  +-- Email gamertag CSVs           (EmailGamertagCsvs Lambda)
        read the recipient list, email every gamertag CSV in one message,
        write the delivery record under the submission

Replay workflow <stack>-replay: Extract text -> Write extracted CSV, for one stored screenshot
CompareRuns Lambda and MaterializeTrainingData Lambda: invoked directly by an operator
  |
  v
Evidence bucket (SSE-KMS, versioned, Object Lock GOVERNANCE 365 days)
```

**Ownership rules:** `process-email` owns submissions and source screenshots. `extract-text` owns processing runs, the Textract request and response, normalized observations and the run completion. `write-extracted-csv` owns the run's export artifacts. `write-gamertag-csvs` owns the submission's per-gamertag export files. `email-gamertag-csvs` owns the submission's results email and its delivery record. `compare-runs` and `materialize-training-data` only read runs and write their own new objects. `scoreboard-logic` and `csv` are pure and perform no I/O. Only Lambda entry points construct AWS SDK clients; every handler's core function receives its I/O as an injected dependencies object so tests run without AWS.

**Packaging:** one npm workspace, `@mcc/match-to-csv`, with Lambda sources under `src/lambdas/`, pure libraries under `src/lib/`, and the CDK app under `cdk/`. The payload types that cross Lambda and state-machine boundaries live in `@mcc/contracts` so later applications can read the same evidence.

### 3.1 Execution policy

- One email is one submission and one execution of the main workflow. One accepted screenshot is one `Map` item and one processing run.
- At most two screenshots from one email are processed at a time, which bounds Textract throughput per message.
- Every evidence write uses `If-None-Match: *`. No stage overwrites an object. A retried stage writes under a new identifier, except the two export stages, which treat an existing object as already written (§6.4), and the roster snapshot, which every run of one roster version shares and which is accepted when its hash matches (§7.1 step 4).
- A Lambda failure fails its state. The workflow retries only the transient errors listed in §6.3, then fails the execution. Earlier evidence stays in place.
- The extraction stage never calls Textract on bytes whose SHA-256 differs from the hash recorded at intake.
- The workflow never deletes, moves or rewrites evidence. Expiry is a bucket lifecycle concern owned by the foundation (§13.1).

## 4. Email intake interface

### 4.1 Addresses and routing

| Deployment | Recipient | Receipt rule owner | Raw object prefix | Evidence namespace |
| --- | --- | --- | --- | --- |
| Stable `dev` or `prod` | `<alias>@<domain>` | Foundation (`aws_ses_receipt_rule.store_raw_email`, rule `submit`) | `incoming/<env>/` | bucket root (`submissions/`, `datasets/`) |
| Ephemeral `<name>` in dev | `<alias>+<name>@<domain>` | Ephemeral stack (`StoreRawEmail`, rule named after the stack) | `incoming/<name>/` | `ephemeral/<name>/` |

- A Region has one active receipt rule set, so the foundation creates `mcc-inbound-<env>`, activates it only after the shared rule exists, and publishes its name, the alias, and the domain in SSM. The alias and domain come from `<ENV>_MCC_EMAIL_ALIAS` and `<ENV>_MCC_EMAIL_DOMAIN` repository secrets. Stacks read them; nothing in source control holds either. The rule named `submit` keeps that AWS name whatever the alias is.
- An ephemeral rule keeps the alias and domain from its last deploy. Its `process-email` reads both parameters for every message and rejects one whose SES recipients, from the `for` clause of the topmost `Received` header, do not include the current `<alias>+<name>@<domain>`. SES lists only recipients a rule accepted, so a stale rule never lists the current address. It records the rejection code `RECIPIENT_NOT_ALLOWED`, stores no attachment, and keeps the raw MIME. A stale rule therefore accepts nothing.
- Every rule enables SES spam and virus scanning, accepts optional TLS, writes the raw MIME message with an S3 action, then stops rule-set evaluation.
- The foundation ignores rule ordering (`after`) on the shared rule so ephemeral rules can be added to the set without drift.

### 4.2 Trigger

The raw-email bucket sends events to EventBridge. The stack's rule matches `aws.s3` `Object Created` events for the raw-email bucket with a key prefix of `incoming/<route>/` and starts the main workflow with input `{ "bucket": <bucket>, "key": <key>, "receivedAt": <time> }`, where `receivedAt` is the event's `time`, when S3 stored the message, as ISO 8601. A manual start may send only `bucket` and `key` (§6.1). EventBridge retries delivery up to three times within two hours and then sends the event to the `<stack>-events-dlq` queue, which uses SQS-managed encryption and keeps messages for 14 days.

### 4.3 Attachment acceptance

The intake Lambda parses the message with `mailparser` and walks attachments in order. For each attachment:

| Check | Rejection code | Notes |
| --- | --- | --- |
| Content type does not start with `image/` | `NOT_AN_IMAGE` | Recorded in the submission; the bytes are not copied to the evidence bucket. |
| Sharp cannot read the metadata, or reports no format | `UNREADABLE_IMAGE` | The original is still stored. |
| Format is not `png`, `jpeg` or `jpg` | `UNSUPPORTED_IMAGE_FORMAT` | Textract byte input accepts PNG and JPEG. |
| Larger than 10 MiB | `IMAGE_TOO_LARGE` | Textract's synchronous byte limit. |
| Narrower than 640 px or shorter than 360 px | `IMAGE_TOO_SMALL` | Too small to read reliably. |

Codes accumulate, so one attachment can carry several. An image with no codes becomes an accepted `SourceScreenshot` with `acquisitionType: SCREENSHOT`; v1 never sets `PHOTO` or `OTHER`, which are reserved for later classification. Attachment names are normalized with NFKC, reduced to `[a-zA-Z0-9._-]`, trimmed of leading and trailing hyphens and cut to 160 characters, falling back to `attachment-<n>`.

### 4.4 Match date and error reply

The plain-text body of each email must contain a valid match date. Surrounding text and signatures are allowed. Screenshots of one session can run from 10pm to 1am the next day, so the date cannot be derived from timestamps.

- Use the first valid calendar date in plain-text reading order, skipping invalid candidates. Dates use `M/D/YYYY`: month 1 to 12, a day that exists in that month, and a four-digit year. Leading zeros are accepted. A candidate touching a digit or slash is ignored, so a longer numeric date token cannot supply a date substring. Only text/plain parts count; HTML-only messages have no match date.
- The intake Lambda checks the date after sender screening (SES verdicts, the sender allowlist and the recipient check) and before attachment acceptance (§4.3). A valid date is recorded as `matchDate` (`YYYY-MM-DD`) in `ingestion.json` and returned in `ProcessEmailOutput`.
- A missing or invalid date rejects the submission with `MATCH_DATE_INVALID`. No attachment is stored and `process-email` returns `ProcessEmailRejectedOutput` (§10.1) instead of `ProcessEmailOutput`, so no screenshot reaches the attachments `Map` or Textract. The raw MIME stays.
- For `MATCH_DATE_INVALID` only, and only when the sender allowlist lists the sender, the Lambda replies to the `From` address from `noreply@<domain>`. The domain is the `/mcc/<env>/match-to-csv/email-domain` parameter, resolved at deploy time. The subject is `Re: <original subject>`, `In-Reply-To` and `References` name the original message ID, and the plain-text body says no valid match date was found in the plain-text body and asks for a date as `M/D/YYYY`. It explains that the first valid date is used and surrounding text and signatures are allowed. It asks the sender to send the email again to the submission address, because replies to the no-reply address are not read.
- No other rejection sends a reply. Screening runs first and the reply needs an allowlisted sender, so a reply goes only to an address on the allowlist.
- A failed send is logged with the SES error name, never an address or email content, and does not change the rejection record.
- Each account's SES domain identity, with DKIM and a custom MAIL FROM, exists outside OpenTofu. An account in the SES sandbox delivers only to verified addresses.

### 4.5 CSV recipient list

The people who receive each submission's per-gamertag CSVs (§8.6.1) are listed in the recipient table, `<project>-<env>-csv-recipients` (§13.1). It is a change log laid out like the gamertag roster table ([spec 1.2 §5.1](1.2-gamertag-roster.md#51-roster-table)), in its own table so addresses stay apart from gamertags and a stack can be granted the list alone. `email-gamertag-csvs` reads the table to send each submission's CSVs (§8.6.2).

| Item | `pk` | `sk` | Attributes |
| --- | --- | --- | --- |
| Head | `RECIPIENTS#<namespace>` | `HEAD` | `recipientsVersion`, `recipientsSha256`, `updatedAt` |
| Change | `RECIPIENTS#<namespace>` | `CHANGE#<recipientsVersion, 10 digits>` | `RecipientChange` (§10.1): `recipientsVersion`, `action` (`ADD`, `DEACTIVATE` or `REACTIVATE`), `recipientId` (a UUID assigned by `ADD`), `address`, `reason`, `actorArn`, `clientRequestId`, `changedAt` |

- **Namespaces and rules.** `<namespace>` is `stable` for stable stacks and `ephemeral/<name>` for ephemeral ones. Spec 1.2 §5.3 rule 1 applies: change items are created once and never updated or deleted, and `HEAD` is the only item that changes. A namespace with no `HEAD` has version 0 and an empty list.
- **Fold.** `foldRecipients` in `@mcc/recipients` folds the log as spec 1.2 §5.1 folds the roster, keyed by `recipientId`. A gap in versions, an `ADD` of an existing `recipientId`, or an action on an entry in the wrong state fails with `RecipientsIntegrityError`, whose message names versions and IDs, never an address.
- **Hash.** `recipientsSha256` is the SHA-256, as lowercase hex, of the UTF-8 JSON array of active entries `{ "address", "recipientId" }` sorted by `recipientId` bytewise, with object keys sorted and no whitespace. The empty list hashes `[]`.
- **Validation.** An address is trimmed and must have no whitespace or comma, exactly one `@` with a non-empty local part and domain, and at most 254 characters. Addresses compare ignoring case. `checkRecipientChange` refuses `INVALID_ADDRESS`; `DUPLICATE_ADDRESS` when an entry, active or inactive, has the same address ignoring case; `RECIPIENT_NOT_FOUND` when no entry, or more than one, has the address a deactivate or reactivate names; `ALREADY_INACTIVE`; and `ALREADY_ACTIVE`. `reason` and `clientRequestId` follow spec 1.2 §4.3 and otherwise fail as `INVALID_REQUEST`. There is no key conflict or near-match check. A `HEAD` condition that fails on 3 attempts is `CONCURRENT_CHANGE`, and a fold that does not match `HEAD` is `RECIPIENTS_INTEGRITY`.
- **Script.** `npm run recipients -- --environment <dev|prod> [--ephemeral <name>] [--profile <profile>] <command>` offers `list [--inactive | --all]`, `history [--after <version>]`, `add <address>... [--reason <text>] [--yes]`, `deactivate <address> [--reason <text>] [--yes]` and `reactivate <address> [--reason <text>] [--yes]`. It behaves as spec 1.2 §4.2 and §6.1 describe the roster script, with the shared account check from `scripts/account-guard.mjs`, the table name from `/mcc/<env>/recipients/table-name`, the `RECIPIENTS#<namespace>` partition, and `checkRecipientChange` in place of `checkChange`. `list` prints each entry's `address`, `status`, `recipientId`, `addedVersion` and `lastChangedVersion`, sorted by address ignoring case. `deactivate` and `reactivate` find the entry by a case-insensitive exact match. Writes print no near-key warning. Exit status is 0 on success, 1 on a refused change or declined confirmation, and 2 on a usage, account, transport or integrity error.

## 5. Evidence model and storage layout

### 5.1 Layout

```text
[ephemeral/<name>/]submissions/{submissionId}/
  ingestion.json
  completion.json
  events/{occurredAt}-{eventId}.json
  export/gamertags/{gamertagFile}.csv
  export/csv-email.json
  screenshots/{screenshotId}/
    source/original
    source/metadata.json
    runs/{runId}/
      manifest.json
      events/{occurredAt}-{eventId}.json
      textract/request.json
      textract/raw-response.json
      normalized/observations.json
      export/extracted-table.json
      export/extracted.csv
      completion.json
[ephemeral/<name>/]datasets/{datasetId}/
  manifest.json
  train.jsonl
  validation.jsonl
  test.jsonl
[ephemeral/<name>/]roster/versions/{rosterVersion}.json
```

A run's prefix derives from its source key (`<source prefix>/runs/<runId>`), so a replayed run of an ephemeral screenshot stays in the ephemeral namespace. Every identifier is `evidenceId()`: the current time in base-36 milliseconds, a hyphen, and a random UUID. Identifiers sort roughly by creation time.

`{gamertagFile}` derives from the roster gamertag: letters and digits stay, each space becomes `_`, and `#` becomes `-`, so `Player 02#7` is `Player_02-7.csv`. Roster gamertags match `^[A-Za-z0-9 ]{1,16}(#[0-9]{1,4})?$` ([spec 1.2 §4.3](1.2-gamertag-roster.md#43-validation-and-errors)) and never hold `_` or `-`, so two gamertags never share a name, and every name is safe in S3 keys and URLs without escaping. Gamertags are unique ignoring case, so two names never differ only in case. A gamertag outside that pattern fails the step with `InvalidGamertagError`.

### 5.2 Rules

1. Evidence is immutable. Every object is written once with `If-None-Match: *`. A conflicting write fails, except in the two export stages (§6.4) and for a roster snapshot whose hash matches (§7.1 step 4).
2. Events are append-only. Each event is its own object, keyed by timestamp and identifier.
3. A replay creates a new run. Nothing modifies an earlier run, its CSV or its events.
4. The Textract request record is written before the provider call, so a failed or timed-out invocation still leaves a record of the attempt.
5. A run records the deployed Git commit, the deployment environment, the source hash and the version of every stage.
6. Unknown layouts stay `UNKNOWN`. Validation flags values; it never edits them.

## 6. Processing pipeline

### 6.1 Main workflow

`<stack>` is a Standard state machine with a 15-minute timeout, X-Ray tracing, and `ALL`-level logging with execution data to `/aws/vendedlogs/states/<stack>`.

1. **Process email and attachments** invokes `ProcessEmail` with `ProcessEmailInput`, the trigger input's `bucket`, `key` and `receivedAt`, and replaces the state with its `ProcessEmailResult` (§10.1). An accepted output has `receivedAt` only when the input had a well-formed one.
2. **Rejected?** is a `Choice` on `$.status`. A `REJECTED` result goes to the `Succeed` state **Submission rejected**, so a submission rejected as a whole ends its execution as succeeded and runs no OCR. Every other result goes to **Process attachments**. The intake task has no `Catch`, so an error it throws still fails the execution.
3. **Process attachments** is a `Map` over `$.screenshots` with a maximum concurrency of 2. Each item is `{ "source": <SourceScreenshot> }`. Results go to `$.results`.
4. Inside each item, **Extract text** invokes `ExtractText` and returns `ExtractTextOutput`, then **Write extracted CSV** invokes `WriteExtractedCsv` and stores its output at `$.summary`.

5. **Write gamertag CSVs** runs after the `Map`. It invokes `WriteGamertagCsvs` with `WriteGamertagCsvsInput`: `submissionId`, `matchDate` and `receivedAt` from the state, and `exports`, each item's `$.summary` in `screenshots` order. It stores its `WriteGamertagCsvsOutput` at `$.gamertagCsvs` (§8.6.1).
6. **Email gamertag CSVs** runs after either variant of step 5. It invokes `EmailGamertagCsvs` with `EmailGamertagCsvsInput`: `submissionId`, `matchDate`, `screenshotCount` (`States.ArrayLength($.screenshots)`) and `gamertagCsvs` from the state. It stores its `EmailGamertagCsvsOutput` at `$.csvEmail` and ends the execution (§8.6.2).

Every task payload also carries `trace` ([spec 1.3 §4.1](1.3-match-to-csv-observability.md#41-trace-context-inputs)).

`receivedAt` is optional. A JSONPath payload field fails the execution when its path is missing, so a `Choice` on `$.receivedAt` comes before steps 1 and 5: **Input has receivedAt** and **Email output has receivedAt**. When the field is missing, they run **Process email and attachments without receivedAt** and **Write gamertag CSVs without receivedAt**, which do the same work with a payload that leaves `receivedAt` out. This covers a manual start with only `bucket` and `key`, and a `receivedAt` that `ProcessEmail` dropped as malformed.

A failure in any item fails the `Map` and the execution, so **Write gamertag CSVs** never runs and the submission gets no per-gamertag file. Items that already finished keep their evidence. The step's input and output hold keys, the match date, trace context, `receivedAt` when present, and counts only, so no roster gamertag enters Step Functions state. Step 6's input and output hold the same values plus the delivery status, the SES message ID and the recipient list version, so no address enters it either.

### 6.2 Replay workflow

`<stack>-replay` is a Standard state machine with a 15-minute timeout and X-Ray tracing. Its input is `ProcessingRunInput`, an existing `SourceScreenshot` under `source`. It runs **Replay extract text** and then **Replay write extracted CSV**, with the same Lambdas and retries as the main workflow, and creates a new run beside the earlier ones. The stack exports its ARN as `ReplayStateMachineArn`.

### 6.3 Retries

Every task disables the default service-exception retry and declares one explicit policy: an initial interval of 2 seconds, a backoff rate of 2 and at most 3 attempts, for these errors:

```text
Lambda.ClientExecutionTimeoutException  Lambda.ServiceException  Lambda.AWSLambdaException
Lambda.SdkClientException  Lambda.TooManyRequestsException
Textract.InternalServerError  Textract.ProvisionedThroughputExceededException  Textract.ThrottlingException
InternalServerError  ProvisionedThroughputExceededException  ThrottlingException
```

A retried intake creates a new submission identifier, and a retried extraction creates a new run identifier, so retries never collide with partial evidence from the failed attempt.

### 6.4 Export idempotency

`write-extracted-csv` writes its two objects concurrently. If either write fails with HTTP 412 (the object already exists), the stage treats that object as written and continues, so a retry after a partial export completes instead of failing. Any other storage error fails the stage.

`write-gamertag-csvs` writes each per-gamertag file with `If-None-Match: *` and treats HTTP 412 the same way, so a retried step completes after a partial write. The same runs give the same files, so an existing file already holds what the retry would write. Any other storage error fails the step under its own error name, with a message that leaves out the key.

`email-gamertag-csvs` first looks for the submission's `export/csv-email.json`. When it exists, the step returns its outcome and sends nothing, so a retry after a recorded send does not email twice. A retry after a send whose record write failed sends again. A record that another attempt wrote first, found as HTTP 412, wins the same way.

## 7. OCR extraction and normalization

### 7.1 Extraction run

`runExtraction(event, dependencies)` performs these steps in order:

1. Create a `runId`, write `manifest.json`, then append `RUN_STARTED`.
2. Read the original image and its Sharp metadata.
3. Refuse the image with `SourceHashMismatchError` when its SHA-256 differs from `source.sha256`, `ImageTooLargeError` when it exceeds 10 MiB, or `UnsupportedImageFormatError` when it is not PNG or JPEG. Textract is not called.
4. Read the roster of the stack's namespace and make sure the version's snapshot exists in the evidence bucket ([spec 1.2 §6.2](1.2-gamertag-roster.md#62-roster-read-and-resolution-in-extract-text) step 4). `RosterIntegrityError` (the change log does not reproduce `HEAD`) and `RosterSnapshotMismatchError` (the stored snapshot differs) fail the run. Textract is not called.
5. Write `textract/request.json`, call `AnalyzeDocument` with the image bytes and `FeatureTypes: ['TABLES']`, and write the full response to `textract/raw-response.json`.
6. Sample row colours (§8.3), run `processScoreboardImage` (§8), resolve each row's player name against the roster (§8.7), and normalize every block (§7.2). Write `normalized/observations.json` with the roster reference and each row's `playerResolution`. A board with an unsupported team layout yields no rows and still completes the run.
7. Write a `SUCCEEDED` completion with the roster reference and `playerMatchCounts`, append `RUN_SUCCEEDED`, log `Screenshot processed` with the three counts, and return `ExtractTextOutput` with the roster reference. Its rows carry no `playerResolution`.

On any error after step 1, the stage writes a `FAILED` completion and `RUN_FAILED` with the request reference (when one exists) and the error name and message, then rethrows. A failure to record the failure is logged at `ERROR` and does not mask the original error.

### 7.2 Normalized observations

The normalizer keeps every provider block and adds derived records. Observation identifiers are `<runId>:<kind>:<providerBlockId>`.

- **Blocks:** every block with its type, text, confidence, geometry, page, row and column index and span, entity types, selection status, relationships and text type.
- **Tables:** one record per `TABLE` block with its index in response order, confidence, geometry, child cell identifiers and a `classification` of `SCOREBOARD` when the header maps `PLAYER` and at least two semantic fields, otherwise `UNKNOWN`.
- **Cells:** one record per `CELL` block. `observedText` joins the cell's child token text with spaces. `tableLocation` holds table, row and column indexes and spans. `semanticLocation` holds the mapped field (`PLAYER`, `SCORE`, `KILLS`, `ASSISTS`, `DEATHS` or `UNKNOWN`) and `rowRole` (`HEADER` for row 1, otherwise `DATA`). `parsed` holds the expected type, whether parsing succeeded, the string value, the integer value when the text is all digits, and an empty `transformations` list.
- **Tokens:** `WORD`, `LINE` and `SELECTION_ELEMENT` blocks with their parent cell when one exists.
- **Geometry:** `imageArtifactId` (the screenshot ID), the normalized bounding box and the polygon. Coordinates refer to the stored original image.

Header text maps to a field per table: text containing `PLAYER` maps to `PLAYER`; text equal to `SCORE`, `KILLS`, `ASSISTS` or `DEATHS` maps to that field. Matching is case-insensitive after trimming.

### 7.3 Deterministic validation

Validation version `scoreboard-validation-v2` evaluates each cell:

| Flag | Condition | Severity |
| --- | --- | --- |
| `EMPTY_REQUIRED_CELL` | observed text is empty | `WARNING` |
| `LOW_TEXTRACT_CONFIDENCE` | confidence below 95 (records `actual`) | `WARNING` |
| `INVALID_INTEGER` | a `DATA` cell in a `SCORE`, `KILLS`, `ASSISTS` or `DEATHS` column whose non-empty text is not all digits | `WARNING` |

A cell is `valid` when it is non-empty and has no invalid integer. `deterministicReviewRequired` is true when any flag applies. Flags never change the observed text.

## 8. Scoreboard parsing

`processScoreboardImage(blocks, rowColors)` in `src/lib/scoreboard-logic.ts` is a pure function. It never calls AWS or Sharp. It returns `{ rows, noRowsReason? }`, where `noRowsReason` is set only when §8.4 rejects the team layout.

### 8.1 Table selection

Each `TABLE` block is scored on its row-1 cells: 3 points for a header containing `PLAYER` and 1 point for each header equal to `SCORE`, `KILLS`, `ASSISTS` or `DEATHS`. The highest score wins; ties keep response order. With no table, or a table without relationships, the result is empty. Only the selected table becomes CSV rows; normalized observations keep every table.

### 8.2 Columns and player rows

1. Build a row-by-column grid of cell text, joining `WORD` children with spaces.
2. The lowest row index is the header. Map recognized headers to `player`, `score`, `kills`, `assists` and `deaths`.
3. Any field left unmapped falls back to the header's columns in order: player first, then score, kills, assists and deaths.
4. For each later row, tidy the player name: drop words that hold no letter, digit or square bracket, remove one leading clan tag in square brackets, and collapse runs of whitespace. Gamertags hold only letters, digits and spaces, so a dropped word is an icon Textract read as text, such as the chat bubble MCC draws as `...`. Skip rows with an empty name.
5. Skip rows where neither score nor kills is all digits. This drops totals, footers and other non-player rows.
6. Flag player names Textract may have misread (§8.2.1).

#### 8.2.1 Player review flags

A row gets `reviewFlags` when a rule below applies to its player name, and has no `reviewFlags` otherwise. The name's words are the last words of the player cell after the icon filter in step 4, as many as the tidied name holds, so clan-tag words never count. A word without a confidence is skipped, and a name with no known confidence gets no flags. Flags never change the name, which stays as read. Resolving the name against the gamertag roster is a separate stage that does not read the flags (§8.7).

| Code | Condition | `wordConfidence` |
| --- | --- | --- |
| `LOW_WORD_CONFIDENCE` | a name word's `WORD` confidence is below 50 | the lowest name-word confidence |
| `SPLIT_TRAILING_DIGITS` | the name's last word is all digits, the word before it ends in a letter, and either word's confidence is below 90 | the lower of the two |

Each flag records `field: 'player'`. The thresholds come from the two real Halo 3 captures: correctly read gamertag words went as low as 52, a lowercase `l` read as `I` scored 39, and a space inserted before trailing digits split one gamertag into words scoring 55 and 88. Gamertags may contain spaces, so a split read with high confidence is not flagged. A `CELL` block's confidence describes table structure and stays near 89 for every player cell in those captures, so it cannot single out a misread.

### 8.3 Row colour sampling

`computeRowColors` in `src/lib/textract-analysis.ts` computes one `RowColor` per table row index found in `CELL` blocks. `extract-text` and the fixture capture script both call it. For each row it takes the union of its cells' vertical extents, decodes a band one pixel high at the row's vertical midpoint from 10% to 40% of the image width, and records the band's mean red, green and blue. Sharp's `stats()` reads the whole image and ignores `extract()`, so the band is averaged from its raw pixels. Dimensions come from the original image. With unknown dimensions there are no colours.

### 8.4 Team detection and naming

1. Cluster the colours of the player rows greedily in input order. The header and rows §8.2 dropped take no part, so a shaded header cannot form a team. A row joins the nearest existing cluster when the Euclidean RGB distance is at most 40, and the cluster's mean updates. Otherwise it starts a new cluster.
2. Only two-team boards are supported. When no player row has a colour, or the player rows form one cluster or three or more, the result has no rows and `noRowsReason` is `{ code: 'UNSUPPORTED_TEAM_LAYOUT', colorClusterCount }`. The count is 0 when no player row has a colour. Free-for-all and three-team boards end here.
3. With exactly two clusters, name each cluster from the HSV values of its mean colour:

| Name | Rule (hue in degrees, saturation and value from 0 to 1) |
| --- | --- |
| Red | hue >= 345 or < 10 |
| Brown | hue 10 to 25 with value < 0.55 or saturation < 0.55 |
| Orange | hue 15 to 35 with saturation >= 0.45 |
| Gold | hue 35 to 60 with value >= 0.55 |
| Green | hue 95 to 140 |
| Blue | hue 200 to 250 |
| Purple | hue 260 to 290 |
| Pink | hue 290 to 345 |
| Fallbacks | value < 0.45 and saturation < 0.45 is Brown; hue 55 to 95 is Gold; otherwise the nearest hue target among Red 0, Orange 25, Gold 50, Green 120, Blue 225, Purple 275, Pink 315, Brown 20 |

Rules apply in table order and the first match wins. When both clusters receive the same name, the second becomes `<name> 2`. A player row without a colour has an empty team.

### 8.5 Win and loss

- The winning team is the team of the player row with the lowest row index.
- Every row on the winning team has `win = 1, loss = 0`. Every other row, including a row with no team, has `win = 0, loss = 1`.

### 8.6 CSV format

`write-extracted-csv` reads `normalized/observations.json` from the `normalizedArtifact` it receives. It fails with `NormalizedObservationsMismatchError` when the document's `runId` or `roster` differs from its input's, or when it holds no `parser.rows`. It writes those rows, each with its `playerResolution`, and the roster reference to `export/extracted-table.json`, and renders the same rows as the CSV.

`rowsToCsv(rows)` writes the header `Team,Player,Score,Kills,Assists,Deaths,Win,Loss,PlayerMatch`, then one line per row in table order. Every value, including the header and the numeric flags, is wrapped in double quotes with embedded quotes doubled. Lines end with `\n`, including the last. Statistics are written exactly as observed. `Player` and `PlayerMatch` follow the row's `playerResolution` ([spec 1.2 §7.6](1.2-gamertag-roster.md#76-csv-rendering)):

| `playerResolution.status` | `Player` | `PlayerMatch` |
| --- | --- | --- |
| `EXACT` | the roster gamertag, equal to the name as read | `EXACT` |
| `RESOLVED` | the roster gamertag | `RESOLVED` |
| `UNMATCHED` | the name as read | `UNMATCHED` |
| no `playerResolution` | the name as read | empty |

The CSV and the per-gamertag files (§8.6.1) are the only artifacts that show the roster gamertag in place of the name as read. `ExtractTextOutput`, `parser.rows` in normalized observations, and `export/extracted-table.json` keep `player` as read, and the last two record the resolution beside it. The CSV leaves out `reviewFlags` and, for `RESOLVED` rows, the name as read; `export/extracted-table.json` keeps both.

#### 8.6.1 Per-gamertag export

After every screenshot of a submission succeeds, `write-gamertag-csvs` writes one CSV per roster gamertag to `submissions/{submissionId}/export/gamertags/{gamertagFile}.csv` (§5.1), in the submission's namespace. These files use the legacy spreadsheet's format, so a person can paste each one into that player's sheet without editing it. The format applies only to these files. Every other artifact, including each run's `extracted.csv` and `extracted-table.json`, stays as above.

1. Check that `matchDate` is `YYYY-MM-DD` and that every entry of `exports` is the `export/extracted.csv` of one of this submission's runs, `[ephemeral/<name>/]submissions/{submissionId}/screenshots/{screenshotId}/runs/{runId}/export/extracted.csv`, all in one bucket. Anything else fails with `InvalidGamertagExportInputError` before any read.
2. Read the `export/extracted-table.json` beside each entry. A document that is not `extracted-table/v1` for that entry's `runId`, or holds no `rows`, fails with `ExtractedTableMismatchError` before any write.
3. Keep the rows whose `playerResolution.status` is `EXACT` or `RESOLVED`, and group them by `playerResolution.gamertag`. `UNMATCHED` rows and rows without a `playerResolution` appear in no file. They stay in each run's `extracted.csv` and in the evidence.
4. Write one file per gamertag with one line per kept row, in the order of `ProcessEmailOutput.screenshots`, then table order within a screenshot. A submission without a kept row writes no file.
5. Log `Gamertag CSVs written` and return `WriteGamertagCsvsOutput`: the submission ID, the export prefix, the file count and the line count. File keys name gamertags, so neither the output nor the log lists them, and errors name run IDs and row positions only.

`rowsToGamertagCsv(matchDate, rows)` writes no header. Each line has these columns, in this order:

| Column | Value |
| --- | --- |
| Date | The submission's `matchDate` as `M/D/YYYY` with no leading zeros (`exportDate`), the same on every line of every file |
| Kills | `kills` as observed |
| Assists | `assists` as observed |
| Deaths | `deaths` as observed |
| Win | `1` when `win` is 1, otherwise empty |
| Loss | `1` when `loss` is 1, otherwise empty |

The player is the file, so there is no player, team, score or match-status column. A value is quoted, with embedded quotes doubled, only when it holds a comma, a quote or a line break, so a line of digits such as `3/7/2026,12,3,4,1,` pastes as is. Lines end with `\n`, including the last.

#### 8.6.2 Results email

After `write-gamertag-csvs` succeeds, `email-gamertag-csvs` emails the submission's per-gamertag CSVs to the CSV recipient list (§4.5) and records the outcome in `export/csv-email.json` (§5.3).

1. Check that `submissionId` is a submission ID, `matchDate` is `YYYY-MM-DD`, `screenshotCount` is a whole number, and `gamertagCsvs` is this submission's output with the export prefix in this stack's namespace. Anything else fails with `InvalidCsvEmailInputError` before any read.
2. When `export/csv-email.json` exists, return its outcome (§6.4).
3. List `export/gamertags/`. Unless it holds exactly `gamertagCsvs.fileCount` CSVs, fail with `GamertagCsvsMissingError`.
4. Read `HEAD` and the change log of the `RECIPIENTS#<RECIPIENTS_NAMESPACE>` partition with consistent reads, fold them with `foldRecipients`, and check the result against `HEAD.recipientsSha256`. A mismatch, or an active address that `normalizeAddress` would change, fails with `RecipientsIntegrityError`, whose message names versions and IDs only. A partition without `HEAD` is version 0 with no entries.
5. With no CSV, record `NO_FILES`. With no active recipient, record `NOT_CONFIGURED`. Neither sends anything.
6. Otherwise send one raw MIME email through SES `SendEmail` from `noreply@<domain>`, with every active address in `To`. The subject is `MCC match <M/D/YYYY>: gamertag CSVs`, using `exportDate`. The plain-text body names the match date, the number of files and screenshots, and the submission ID. Each CSV is its own `text/csv` attachment named by its file name. Record `SENT` with the SES message ID.
7. Write the record create-only, log the outcome, and return `EmailGamertagCsvsOutput`. The log and output hold the status, message ID, recipient list version and counts only.

SES `TooManyRequestsException` is rethrown as `ThrottlingException` and an SES server fault as `InternalServerError`, so the retry policy in §6.3 retries them. Any other SES error keeps its name and fails the execution, which fires the workflow failure alarm in prod. Every SES and storage error is rethrown with a message that names only the error, never an address or a key. The CSVs stay in S3 whatever the outcome.

### 8.7 Player resolution

After parsing, `extract-text` passes the rows and the active entries of the roster version it read to `resolvePlayers` from `@mcc/roster` ([spec 1.2 §7](1.2-gamertag-roster.md#7-matching)). Each row gets one `PlayerResolution`: `EXACT` when a roster gamertag equals the name as read, `RESOLVED` when the name as read is a near reading of exactly one roster gamertag, and `UNMATCHED` with a reason otherwise. Every row is `UNMATCHED` with `NO_CANDIDATE` while the roster is empty.

The resolution is recorded as `playerResolution` on the row in `parser.rows` of the normalized observations, and nowhere else in this stage. It never changes the row's `player` or `reviewFlags`, or any cell's `observedText`. `ExtractTextOutput.rows` carry no `playerResolution`, so no roster gamertag enters Step Functions state. The run completion records how many rows are `EXACT`, `RESOLVED` and `UNMATCHED` as `metrics.playerMatchCounts`, and the manifest records the matcher's `rosterMatcherVersion` (§5.4).

## 9. Replay, comparison and training data

### 9.1 Replay

An operator starts the replay workflow with an existing `SourceScreenshot` (§6.2), usually copied from `source/metadata.json`. The new run records the current stage versions and commit, so replaying after a parser change produces a comparable run without altering the original.

### 9.2 Run comparison

The `CompareRuns` Lambda (exported as `RunComparisonFunctionName`) takes `{ bucket, baselineKey, candidateKey, outputKey }`.

- Both input keys must end in `/normalized/observations.json`. The output key must end in `.json` and differ from both inputs. Both runs must belong to the same screenshot when both record one.
- Cells are matched on `tableIndex:rowIndex:columnIndex`. A coordinate is reported when it exists in only one run, or when its text or confidence differs.
- The output (`run-comparison/v1`) holds the screenshot ID, both run IDs, `comparedAt`, a summary of baseline, candidate and changed cell counts, and the list of changes with before and after text and confidence. It is written once and returned.

### 9.3 Training-data materialization

The `MaterializeTrainingData` Lambda (exported as `TrainingDataMaterializerFunctionName`) takes `{ bucket, normalizedKeys, splitSeed? }` with 1 to 1,000 keys. It deduplicates and sorts the keys, reads each normalized artifact with the run manifest beside it, and writes a dataset under `[ephemeral/<name>/]datasets/<datasetId>/`.

- **Split:** `sha256(splitSeed + "\0" + screenshotId)`, first four bytes as an unsigned integer, modulo 10,000. Below 8,000 is `TRAIN`, below 9,000 is `VALIDATION`, otherwise `TEST`. The default seed is `ocr-cells-v1`. Every cell and every replayed run of one screenshot lands in the same split.
- **Records:** one `ocr-cell-example/v1` line per cell, joining the cell, its tokens, its validation result, the run's stage versions and build, the source artifact and the normalized artifact reference, with `labelStatus: UNLABELED`.
- **Manifest:** `ocr-cell-dataset/v1` with `datasetId`, `createdAt`, `splitAlgorithm: sha256-screenshot-80-10-10-v1`, `splitSeed`, `labelStatus`, cell `counts` and `screenshotCounts` per split, the three file references, and one source entry per run.

### 13.6 Delivery

CI synthesizes the stack and verifies bundles on every affecting change. Merging a release pull request to `main` publishes component releases. `Release: release PR` selects only application releases from Release Please's per-path outputs and, when there is at least one, starts `Delivery: deploy application releases` on `main` with them. Each released application deploys to dev at its full release commit SHA and then, after its own successful dev deployment and a required reviewer approval, to prod. Ordinary merges and shared-package-only releases deploy nothing. For `match-to-csv` the deploy job runs on an ARM64 runner and:

1. Verifies the deployment request, the checked-out SHA and the target account.
2. Reads the CDK bootstrap version parameter and the seven foundation parameters it needs (raw-email bucket, evidence bucket, data key, rule set name, domain, `/mcc/<env>/roster/table-name`, and `/mcc/<env>/recipients/table-name`), and fails if any is missing.
3. Masks the domain in all later log lines, then checks that the foundation rule set is the active one, that the SES identity for the domain is verified, and that the domain's MX record targets `inbound-smtp.<region>.amazonaws.com`.
4. Synthesizes, verifies bundles, and prints a CDK diff for prod.
5. Records a GitHub deployment, deploys, and verifies the stack status, that every Lambda is `Active` with a `Successful` last update, and that both state machines are `ACTIVE`.

Prod requires an Environment with required reviewers and administrator bypass disabled. Each deployment record stores its release tag. Forward deploys and rollback share one queue per application and environment with no cancellation of running deploys. After approval and inside the queue lock, a forward deploy skips successfully when its version is not newer than the latest successful deployment, and writes the reason to its summary. A rollback bypasses this comparison but requires a reason and a published application release tag whose commit previously deployed to prod successfully. Deploy jobs use `refs/heads/main` through `_delivery-deploy-environment.yml`, preserving the CDK role trust.

## 14. Security and privacy

1. No artifact is public. Every bucket blocks public access, and the raw-email bucket denies requests without TLS.
2. Screenshots, OCR text and CSVs contain gamertags. They live only in the evidence bucket, encrypted with the customer-managed key.
3. The receiving domain, recipient addresses, account IDs and real messages never appear in source control, fixtures or logs. The deploy workflow masks the domain before using it.
4. SES scans every inbound message for spam and viruses. Attachments are parsed with `mailparser` and inspected with Sharp using `failOn: 'none'`, so a corrupt image becomes a rejection instead of a crash.
5. Attachment names are normalized before they appear in keys, so a crafted filename cannot change the key structure.
6. Integrity is checked before OCR (§7.1). Object Lock and create-only writes prevent the application from altering evidence.
7. Ephemeral stacks cannot reach shared evidence through key construction: every key they write starts with `ephemeral/<name>/`, their roles carry the local boundary, and the reserved names stop one stack from claiming another's namespace.
8. Roster gamertags live only in the roster table and in the evidence bucket (roster snapshots, resolutions in normalized observations, each run's export, and the per-gamertag files), all encrypted with the data key. `extract-text` logs the roster version and match counts, never a gamertag, and `ExtractTextOutput` carries only the roster reference and rows without `playerResolution`, so no roster gamertag enters Step Functions state. `write-gamertag-csvs` reads gamertags from each run's `extracted-table.json`, and its input, output, log line and error messages hold keys, run IDs, row positions and counts only (§8.6.1).
9. CSV recipient addresses live only in AWS, in the recipient table, which DynamoDB encrypts with the data key, including its point-in-time backups (§4.5). They never enter the repository, fixtures, logs, Step Functions state or the delivery record; only the results email's `To` header holds them (§8.6.2). OpenTofu manages no recipient item, so they never appear in state or plan output. Tests use `example.test` addresses. The recipient script takes addresses only as arguments and prints them only to the administrator's terminal. It reads no input file and writes no file or log. Its integrity errors name versions and IDs, never an address.

## 17. Acceptance criteria

v1 is complete when all of the following hold:

1. An email with two valid screenshots and one PDF to the dev recipient produces one submission with two `ACCEPTED` sources, one `NOT_AN_IMAGE` rejection, two runs with every §5.1 object, and a succeeded execution.
2. An email with only an undersized image produces a `REJECTED` submission with `IMAGE_TOO_SMALL`, a stored original, and an execution that succeeded at **Submission rejected**.
3. A Textract throttling error that persists through retries leaves `RUN_STARTED`, `RUN_FAILED`, the request record and a `FAILED` completion.
4. A two-team screenshot produces a CSV with MCC colour names and the top team marked as winners. A screenshot whose player rows share one colour produces no rows, a `SUCCEEDED` run, and `parser.noRowsReason` with a cluster count of 1.
5. Replaying a screenshot creates a second run without changing the first, and comparing the two runs reports zero changes when the stage versions are unchanged.
6. Materializing runs from at least 20 screenshots places every cell of a screenshot in one split and records the split algorithm and seed.
7. An ephemeral stack receives mail at its plus address, writes only under `ephemeral/<name>/`, and destroys cleanly.
8. Every §16.1 test passes with the coverage thresholds, CDK synthesis succeeds, and `verify:bundle` finds Linux ARM64 Sharp in both Sharp functions.
9. The prod deploy job passes its preflight and post-deploy checks.

## 18. Risks and accepted limitations

1. **Only two-team boards produce rows.** Free-for-all and three-team screenshots produce no rows, and so does a two-team screenshot whose team colours merge at a distance of 40 or less or whose row colours could not be sampled. Each run succeeds, so the only signals are `parser.noRowsReason`, the `Screenshot processed` log line, and in prod the zero-row alarm.
2. **The top row decides the winner.** The parser trusts MCC's ordering. It does not read placement, detect ties or check scores.
3. **Colour naming is heuristic.** The thresholds come from MCC's palette, not from a labeled corpus. Lighting in photographed screens can shift hues, and two similar teams can merge at a distance of 40 or less.
4. **Only one table becomes CSV.** A scoreboard that Textract splits into several tables yields a partial CSV. The normalized evidence keeps every table, so a later parser can recover the rest by replay.
5. **No orientation correction.** A photo whose EXIF orientation tag rotates it will be read as stored. v1 treats every accepted image as a screenshot.
6. **Retries can duplicate work.** A retried intake creates a second submission for the same raw message, and a retried extraction creates a second run. A Lambda timeout can leave a run with `RUN_STARTED` and no completion. Consumers must treat a run without a `SUCCEEDED` completion as incomplete.
7. **GOVERNANCE mode, not COMPLIANCE.** A principal with `s3:BypassGovernanceRetention` can delete locked evidence. That keeps deliberate cleanup possible, at the cost of no protection against a compromised administrator.
8. **Raw MIME expires after 90 days.** Non-image attachments and the original headers are lost after that. Accepted screenshots are kept in the evidence bucket.
9. **Player names reach logs.** Step Functions logs include execution data, which carries attachment names and extracted rows. Log retention is two weeks in dev and three months in prod.
10. **Operator Lambdas trust IAM alone.** `CompareRuns` and `MaterializeTrainingData` accept any key in the bucket. Create-only writes stop them from overwriting evidence, but they can write new objects outside a run.
11. **`EMPTY_REQUIRED_CELL` fires on every empty cell,** including cells in unmapped columns. Reviewers should expect noise there until the validation rules know which columns are required.
12. **Player review thresholds come from two captures.** §8.2.1 separates the misreads in those captures from every correct reading, with a margin of a few points on one side. More captures may show misreads above 50 or correct readings below it. A misread that scores high and keeps the word count, such as `I` for `l` at 90, passes unflagged.
13. **Per-gamertag files cover only the first runs.** The replay workflow writes no per-gamertag file, so a replay that improves a run leaves the submission's files as they were. A submission with a failed screenshot has no per-gamertag file at all, and its other screenshots' rows reach the legacy spreadsheet only by hand.
