# Match-to-CSV observability: Technical Specification

**Status:** Draft

**Version:** 1.3-draft

**Date:** October 18, 2026

**Component:** `applications/match-to-csv` (the four ingest Lambdas, `src/lib/log.ts`, `src/lib/metrics.ts`, CDK stack), `packages/contracts`, and the local deployer policy template in `docs/self-hosting/policies/`

**Runtime:** TypeScript on the Node.js Lambda runtime the stack already uses, ARM64

**Deployment:** the existing match-to-csv CDK stack, one per environment plus ephemeral developer stacks

**Telemetry services:** CloudWatch Logs with embedded metric format (EMF), CloudWatch Logs Insights, CloudWatch metrics, alarms and one dashboard, and the X-Ray active tracing the stack already enables

**Persistent state:** none added. Log groups and metrics are application resources owned by the CDK stack. The S3 evidence events stay the durable record of what happened to an input.

**External dependencies at runtime:** none added. EMF needs no CloudWatch API call or permission.

**Out of scope:** tail sampling, an OpenTelemetry collector, a state store or status table for uploads, Lambda Insights, CloudWatch Application Signals, high-resolution metrics, log metric filters, anomaly-detection alarms, Contributor Insights, metrics per sender or per gamertag, any user-facing progress UI, and any metric, alarm, saved query or dashboard in an ephemeral stack.

The operator of match-to-csv has no application to check it with, so CloudWatch is the only place to answer four questions: what happened to one emailed submission, where each recent upload is now, how much work the pipeline is doing and with what result (emails received, submissions rejected and why, Textract calls, gamertag CSVs written, players matched to the roster), and whether the pipeline is failing, slow, or producing poor OCR. This spec answers them with one structured log record per pipeline stage. In dev and prod the record is also a set of CloudWatch metrics (through EMF), broken down only by values from fixed lists. Logs Insights queries join the records by submission and by Step Functions execution. A rejected submission ends its execution as succeeded, so the failure alarms fire only on real failures. Custom metrics are billed only for the hours they receive data, so at a few submissions a day the design costs about $0 to $2 a month. Ephemeral developer stacks only write the log records, and developers read them with a scoped grant on the local deployer permission set.

## 1. Resolved requirement decisions

| Requirement | Decision | Reason |
| --- | --- | --- |
| Distributed tracing without tail sampling | Every stage writes one wide event (§6). `submissionId` is the trace ID, `screenshotId` and `runId` are span IDs, `executionId` groups one execution, and Logs Insights reassembles the trace (§8). X-Ray stays on and each event records the X-Ray trace ID. | Tail sampling needs a collector to buffer whole traces. At this volume X-Ray's default sampling records nearly every request within the free tier, so the logs only need a pointer to it. |
| Show the progress of uploads | Computed at query time per Step Functions execution (§8.1, Q2). An execution is complete only when `write-gamertag-csvs` succeeds, and Q2 shows how many screenshots have exported before then. Step Functions failure records mark executions that ended without completing. | A state store would duplicate the S3 evidence events and need its own writes, permissions and consistency rules. |
| One event per stage, including replay | The four ingest Lambdas each have a `Stage`: `process-email`, `extract`, `write-csv` and `write-gamertag-csvs`. Replay runs the same `extract-text` and `write-extracted-csv` Lambdas, so replay is recorded as `workflow: "REPLAY"` on their events, not as another `Stage` value. | Keeps the `Stage` dimension aligned with the Lambda that emits it. Replays still separate in every query by `workflow`. |
| When a submission is complete | A submission is complete when `write-gamertag-csvs` succeeds. That step runs only after every screenshot's CSV is written, and its per-gamertag CSVs are the files the sender asked for. | A submission whose screenshot CSVs exist but whose gamertag CSVs failed has not delivered anything usable. |
| Metric dimensions | `Stage` is on every new metric. Three more dimensions are allowed, and each takes values only from a fixed list in code: `Reason` (a `SubmissionRejectionCode` or `AttachmentRejectionCode`), `MatchStatus` (`EXACT`, `RESOLVED`, `UNMATCHED`) and `ErrorClass` (§7.3). IDs, senders, gamertags, raw error names and `workflow` are event fields and never dimensions. | CloudWatch bills each metric name and dimension combination as one custom metric, only for the hours it receives data. A fixed list bounds the count, and a combination that never occurs costs nothing. A free-form value such as an ID or a raw error name would create one billed metric per value. |
| Rejected submissions | `process-email` returns a rejected result instead of throwing. A `Choice` state sends it to a `Succeed` state, so the execution succeeds. The `SUBMISSION_REJECTED` evidence event, the stage event and `SubmissionsRejected` still record it. | A thrown rejection fails the execution and counts as a Lambda error, so every spam or unknown-sender email fires the `ExecutionsFailed` and ProcessEmail `Errors` alarms. Those alarms must mean something broke. |
| Error breakdown | Every `ERROR` event maps its `errorName` to one `ErrorClass` and counts `StageErrors` by `Stage` and `ErrorClass`. The raw `errorName` stays in the event for queries. | Gives the dashboard errors by type and stage over time without one metric per error name. |
| Dashboard log widgets | The dashboard holds two Logs Insights tables: job status (Q2) and errors per hour (Q7). | Job status cannot be a metric without a state store. At a few submissions a day, each refresh scans kilobytes and costs a fraction of a cent. |
| Ephemeral stacks | Log only. They write the same stage events without an `_aws` block, and write no `ExtractedRows` or `ZeroRowExtractions` record. They get no alarms, saved queries or dashboard. | Ephemeral stacks share the dev account and region, so their samples would merge into the stable dev stack's `Stage`-dimensioned metrics and alarms. Developers need the logs, not metrics. |
| Developer access to ephemeral logs | The `MccStatsSuiteLocalCdkDeploy` policy template gains read and query access to `match-to-csv-e-*` log groups only (§8.2). | The template grants no CloudWatch Logs access today, so developers cannot tail or query their own stacks. Scoping to the ephemeral prefix keeps stable dev logs out of reach. |
| Existing `ExtractedRows` and `ZeroRowExtractions` metrics | Unchanged in dev and prod. They keep the `FunctionName` dimension, so the zero-row alarm and its history keep working. | Changing their dimension would break the zero-row alarm for no gain. |
| Step Functions logging | The ingest workflow logs at `ERROR` with `includeExecutionData: false`. The Infrequent Access log class is not used. | `ALL` with execution data logs every transition's payload, including every extracted row, and is the largest log volume in the stack. `ERROR` still records the execution failure, timeout and abort events Q2 reads. The class cannot be changed on an existing log group, and at `ERROR` the volume is too small for its discount to matter. |
| Log format | Lambdas use the JSON log format with application log level `INFO` and system log level `INFO`. | Platform records become structured JSON. `INFO` keeps the `platform.report` record that Q6 reads. |
| End-to-end latency | Measured from the time EventBridge reports the raw email object was created to the time `write-gamertag-csvs` stores the last gamertag CSV. | That is the delay the sender sees, apart from SES delivery. `process-email`'s own `receivedAt` excludes EventBridge and Step Functions start-up time. |

**Additional capabilities included:** saved Logs Insights query definitions and a dashboard in dev and prod.

## 2. Goals and non-goals

### 2.1 Goals

1. Given a `submissionId` or an execution ID, one Logs Insights query lists every stage that handled it, in order, with outcome, duration, run IDs, error names and rejection codes.
2. One query gives each recent execution a status of `COMPLETE`, `REJECTED`, `FAILED` or `IN_PROGRESS`. `COMPLETE` requires a successful `write-gamertag-csvs` event. The query also shows how many screenshots have exported so far, whatever order the branches finish in.
3. The dashboard shows, per hour: emails received, submissions accepted, rejected by reason, and completed, attachments rejected by reason, Textract calls and errors, screenshot and gamertag CSVs written, players matched by match status, and errors by stage and class.
4. CloudWatch alarms fire when end-to-end latency, mean OCR confidence, Textract throttling, the unmatched player rate, or match date replies degrade, in addition to the existing failure alarms.
5. The existing failure alarms fire only on failures, never on a rejected submission.
6. Every custom metric dimension takes values from a fixed list, so the number of billed metrics has a fixed ceiling (§13.6). The design reduces log ingestion compared with the current stack.
7. Ephemeral developer stacks write the same events as logs and nothing else, and a developer with the `mcc-dev` profile can tail and query them.

### 2.2 Non-goals

- Request-level sampling decisions. Every invocation logs its event.
- A durable or queryable status API. Logs expire with their retention (§13.3), and the S3 evidence events remain the system of record.
- Telemetry for `compare-runs` and `materialize-training-data`. They are operator tools invoked by hand, and their Lambda `Errors` alarms already exist (§20, backlog).
- Exactly-once events. A retried Lambda attempt emits its own event (§7.2).
- Developer access to metrics, X-Ray, stable dev logs or prod logs.
- Metrics per sender, per gamertag or per roster entry. Q1 and the S3 evidence answer questions about one sender or player.

## 3. Runtime architecture

```text
SES -> raw email bucket -> EventBridge (Object Created, adds receivedAt = $.time)
  |
  v
Step Functions ingest workflow (each task payload adds trace context)
  +-- process-email        -> stage event, Stage=process-email
  +-- Choice: rejected?    -> Succeed "Submission rejected"
  +-- Map (concurrency 2)
       +-- extract-text    -> stage event, Stage=extract
       +-- write-csv       -> stage event, Stage=write-csv
  +-- write-gamertag-csvs  -> stage event, Stage=write-gamertag-csvs
  +-- workflow log group (ERROR: ExecutionFailed, ExecutionTimedOut, ExecutionAborted)
  |
  v
Lambda log groups (/aws/lambda/<prefix>-<Function>)
  +-- Logs Insights   -> queries Q1..Q7 (saved in dev and prod)
  +-- EMF extraction, dev and prod only -> MCC/MatchToCsv metrics -> alarms, dashboard

Replay workflow -> extract-text, write-csv (trace.workflow = REPLAY)
X-Ray: Lambda and Step Functions segments, linked from events by xrayTraceId
```

**Ownership rules:** only `src/lib/metrics.ts` builds stage events and EMF blocks, and only `src/lib/log.ts` and `src/lib/metrics.ts` write to stdout. Handlers call them with injected writers, as `publishExtractionMetrics` does today. The CDK stack owns every telemetry resource. OpenTofu owns none.

**Packaging:** `TraceContext` and the new optional fields live in `packages/contracts` (§10). No new workspace or dependency. EMF records are built by hand, as today, rather than with `aws-embedded-metrics`.

### 3.1 Execution policy

- Each Lambda invocation writes exactly one stage event, on success and on failure, before it returns or rethrows. This includes failures before `submissionId` exists, such as a raw email read, MIME parse or SSM read failure.
- A whole-submission rejection is a result, not an error. `process-email` records the rejection evidence, writes a `REJECTED` stage event and returns. It throws only when it cannot finish its work.
- Alongside the stage event, an invocation may write breakdown records (§7.1) that carry only metrics. They hold no IDs and are not stage events.
- Metrics are on unless `EMF_METRICS_ENABLED` is exactly `false`. When it is `false`, the event has no `_aws` block and no metric members, and `publishExtractionMetrics` writes nothing. The CDK stack sets `false` in ephemeral stacks only. Dev and prod leave it unset, so functions deployed before the variable exists keep publishing `ExtractedRows` and `ZeroRowExtractions`, and no slice can silence them on its own.
- A failure to build or write the event never fails the invocation. The handler catches it and logs an `ERROR` line.
- Telemetry never changes evidence. Events are not written to S3, and no evidence write depends on telemetry.
- Events never contain screenshot bytes, OCR text, extracted rows, email bodies, subjects, sender addresses or recipient addresses (§14).

## 4. External interface

### 4.1 Trace context inputs

The CDK stack adds these fields to each Lambda task payload. Direct invocations, such as tests and manual replays, may omit them, and the event then omits the matching fields. A manual start of the ingest workflow may also omit `receivedAt` (§13.1).

| Field | Set by | Value |
| --- | --- | --- |
| `receivedAt` on the `process-email` input | EventBridge rule input | `$.time` of the `Object Created` event, ISO 8601 |
| `trace.executionId` | each `LambdaInvoke` payload | `$$.Execution.Id`, the execution ARN |
| `trace.retryCount` | each `LambdaInvoke` payload | `$$.State.RetryCount` |
| `trace.workflow` | each `LambdaInvoke` payload | `INGEST` in the ingest workflow, `REPLAY` in the replay workflow |

`process-email` copies `receivedAt` into its output and every `SourceScreenshot` it emits, so later stages, the gamertag step and replays carry it.

### 4.2 Outputs

The outputs are log records (§6), metrics (§7), saved queries (§8), alarms (§9.1) and a dashboard (§9.2). Handler return values change only by carrying `trace` and `receivedAt` through to the next task where §11 says so, and by `process-email` returning a rejected result instead of throwing (§10.1).

## 5. Identifiers

| Identifier | Created by | Role in the trace |
| --- | --- | --- |
| `submissionId` | `process-email` | Trace ID. Present on every event once `process-email` has assigned it. |
| `executionId` | Step Functions | Groups every event of one ingest execution, including a `process-email` failure before `submissionId` exists. Equals the `execution_arn` field of Step Functions log records. |
| `screenshotId` | `process-email`, one per accepted attachment | Span ID for one screenshot's branch of the `Map`. |
| `runId` | `extract-text`, one per processing run | Attempt ID. A replay creates a new `runId` for the same `screenshotId`. |
| `xrayTraceId` | Lambda runtime (`_X_AMZN_TRACE_ID`, the `Root=` value) | Links to the X-Ray trace map for the invocation. |
| `requestId` | Lambda context (`awsRequestId`) | Links to the invocation's other log lines and its `platform.report` record. |

## 6. Stage event

### 6.1 Fields

Every event is one JSON line. In dev and prod it also carries an `_aws` EMF block (§7.1). Fields that do not apply are omitted, not null.

| Field | Type | Stages | Meaning |
| --- | --- | --- | --- |
| `event` | `"stage.completed"` | all | Fixed value, the filter every query starts with |
| `schemaVersion` | `"stage-event/v1"` | all | Version of this record |
| `Stage` | `process-email` \| `extract` \| `write-csv` \| `write-gamertag-csvs` | all | Metric dimension on every stage metric |
| `workflow` | `INGEST` \| `REPLAY` | all, when `trace` is present | Which state machine invoked the Lambda |
| `outcome` | `OK` \| `REJECTED` \| `ERROR` | all | `REJECTED` only when the whole submission is rejected. A submission with some rejected attachments and at least one accepted screenshot is `OK`. |
| `env` | string | all | `DEPLOYMENT_ENVIRONMENT`, such as `DEV` or `PROD`. Ephemeral stacks are told apart by log group. |
| `gitSha` | string | all | The build SHA already passed to `extract-text`, now passed to every function |
| `submissionId`, `screenshotId`, `runId` | string | where known | §5 |
| `executionId`, `retryCount` | string, number | when `trace` is present | §4.1 |
| `xrayTraceId`, `requestId` | string | all | §5 |
| `durationMs` | number | all | Handler wall-clock time |
| `errorName` | string | `ERROR` only | The error's `name`, such as `ImageTooLargeError` or `ThrottlingException`. Never its message. |
| `ErrorClass` | string | `ERROR` only | The §7.3 class of `errorName`. A metric dimension of `StageErrors`. |
| `rejectionCodes` | string | `process-email`, `REJECTED` | Every `SubmissionRejectionCode`, sorted and joined with `,`, such as `SENDER_NOT_ALLOWED,SPAM_VERDICT_FAILED` |
| `attachmentRejectionCodes` | string | `process-email`, when any attachment was rejected | Every distinct `AttachmentRejectionCode` across rejected attachments, sorted and joined with `,` |
| `attachmentCount`, `screenshotCount`, `rejectedAttachmentCount` | number | `process-email` | Counts only. `screenshotCount` is the number of accepted screenshots and is present on `OK` events. |
| `matchDateReply` | `SENT` \| `FAILED` \| `SKIPPED` | `process-email`, when `MATCH_DATE_INVALID` is among the codes | Whether the match date error reply reached SES. `SKIPPED` means the reply domain was missing. |
| `acquisitionType`, `imageBytes`, `widthPx`, `heightPx` | | `extract` | From `SourceScreenshot` and the image read |
| `rowCount`, `reviewRequiredCells`, `meanConfidence`, `textractMs` | number | `extract` | `meanConfidence` is the mean Textract cell confidence. `reviewRequiredCells` counts cells with `deterministicReviewRequired`. |
| `exactRows`, `resolvedRows`, `unmatchedRows` | number | `extract`, `OK` only | Rows whose `playerResolution` status is `EXACT`, `RESOLVED` or `UNMATCHED`, the counts `extract-text` already computes |
| `rowCount` | number | `write-csv` | Rows in the screenshot CSV |
| `exportedScreenshotId` | string | `write-csv`, `OK` only | Equals `screenshotId`. Q2 counts its distinct values. |
| `fileCount`, `rowCount`, `exportCount` | number | `write-gamertag-csvs` | Gamertag CSVs written, rows across them, and screenshot exports read. Counts only, never gamertags or file names. |
| `endToEndMs` | number | `write-gamertag-csvs`, `OK` only | Only when `receivedAt` is present |
| `completedSubmissionId` | string | `write-gamertag-csvs`, `OK` only | Equals `submissionId`. Q2 counts it to mark the execution `COMPLETE`. |

Codes are joined strings rather than arrays because Logs Insights flattens arrays into numbered fields, and grouping by one numbered field hides the rest.

## 7. Metrics

### 7.1 EMF rules

1. Metrics are published unless `EMF_METRICS_ENABLED` is `false` (§3.1), which only ephemeral stacks set. Every rule below applies to dev and prod.
2. Namespace `MCC/MatchToCsv`, the existing `METRIC_NAMESPACE`.
3. The stage event's metrics are in one `CloudWatchMetrics` directive with `Dimensions: [["Stage"]]`. On an `ERROR` event, `StageErrors` is in a second directive in the same record whose only dimension set is `[["Stage", "ErrorClass"]]`, and it appears in no other directive. EMF applies every dimension set in a directive to every metric in it, so sharing one directive would publish each stage metric under `ErrorClass` too.
4. A metric broken down by `Reason` or `MatchStatus` needs one record per value, because an EMF record holds one value per dimension. Each such value is written as a breakdown record: one JSON line with `event: "metric.breakdown"`, `Stage`, the dimension member, the metric member and an `_aws` block with `Dimensions: [["Stage", "<dimension>"]]`, and nothing else. A breakdown record is written only for a non-zero value. Ephemeral stacks write no breakdown records.
5. Records are written with `process.stdout.write`, never `console.log`, so the runtime cannot prefix or wrap them (the reason recorded in `src/lib/metrics.ts`).
6. A metric is present in a record only when it has a value for that invocation. Count metrics are written on the event that counts and are absent otherwise.

### 7.2 Custom metrics added

| Metric | Unit | Stage | Dimensions | Value |
| --- | --- | --- | --- | --- |
| `SubmissionsAccepted` | Count | `process-email` | `Stage` | 1 when the submission is accepted |
| `SubmissionsRejected` | Count | `process-email` | `Stage` | 1 when the whole submission is rejected |
| `SubmissionsRejected` | Count | `process-email` | `Stage`, `Reason` | 1 per `SubmissionRejectionCode` of a rejected submission, in breakdown records. A submission with two codes counts once under each, so the sum across reasons can exceed the total above. |
| `ScreenshotsAccepted` | Count | `process-email` | `Stage` | Number of accepted screenshots |
| `AttachmentsRejected` | Count | `process-email` | `Stage`, `Reason` | Rejected attachments carrying each `AttachmentRejectionCode`, in breakdown records, on accepted and rejected submissions |
| `MatchDateReplyFailed` | Count | `process-email` | `Stage` | 1 when `matchDateReply` is `FAILED` |
| `TextractLatency` | Milliseconds | `extract` | `Stage` | Time spent in `AnalyzeDocument`, only when the call returned. Its sample count is the number of calls that returned. |
| `OcrMeanConfidence` | Percent | `extract` | `Stage` | `meanConfidence`, only when at least one cell exists |
| `ReviewRequiredCells` | Count | `extract` | `Stage` | `reviewRequiredCells` |
| `PlayerRows` | Count | `extract` | `Stage`, `MatchStatus` | `exactRows`, `resolvedRows` and `unmatchedRows`, one breakdown record each |
| `CsvWritten` | Count | `write-csv` | `Stage` | 1 when the screenshot CSV is stored |
| `GamertagCsvsWritten` | Count | `write-gamertag-csvs` | `Stage` | `fileCount` |
| `SubmissionsCompleted` | Count | `write-gamertag-csvs` | `Stage` | 1 when every gamertag CSV is stored |
| `EndToEndLatency` | Milliseconds | `write-gamertag-csvs` | `Stage` | `endToEndMs` |
| `StageErrors` | Count | all | `Stage`, `ErrorClass` | 1 on every `ERROR` event |

Each retried attempt is its own invocation and its own event, so `StageErrors` counts failed attempts, including attempts a later retry recovered. Final failures come from `AWS/States` `ExecutionsFailed` and from Q2. Replays write the same metrics, so `TextractLatency`, `OcrMeanConfidence`, `ReviewRequiredCells`, `PlayerRows`, `CsvWritten` and `StageErrors` include replay work. A bulk replay therefore counts toward `OcrMeanConfidenceAlarm` and `UnmatchedPlayerRateAlarm` (§18). `SubmissionsAccepted`, `SubmissionsRejected`, `GamertagCsvsWritten`, `SubmissionsCompleted` and `EndToEndLatency` come only from the ingest workflow, because replay runs neither `process-email` nor `write-gamertag-csvs`.

### 7.3 Error classes

`src/lib/metrics.ts` maps `errorName` to `ErrorClass` with a fixed table. A name the table does not list maps to `OTHER`, so a new error never creates a new metric. Adding a name to the table is an ordinary code change.

| `ErrorClass` | Error names |
| --- | --- |
| `TEXTRACT_THROTTLED` | `ThrottlingException`, `ProvisionedThroughputExceededException`, `LimitExceededException` |
| `TEXTRACT` | `InternalServerError`, `InvalidParameterException`, `BadDocumentException`, `UnsupportedDocumentException`, `DocumentTooLargeException` |
| `IMAGE` | `ImageTooLargeError`, `UnsupportedImageFormatError` |
| `ROSTER` | `RosterConfigurationError`, `RosterIntegrityError`, `RosterSnapshotMismatchError`, `RosterSnapshotConflictError` |
| `INTEGRITY` | `SourceHashMismatchError`, `NormalizedObservationsMismatchError`, `ExtractedTableMismatchError`, `InvalidGamertagError`, `InvalidGamertagExportInputError` |
| `CONFIGURATION` | `ParameterNotFound`, `AccessDeniedException` |
| `STORAGE` | `StorageError`, `NoSuchKey`, `NoSuchBucket` |
| `OTHER` | anything else |

### 7.4 Existing metrics kept

In dev and prod, `ExtractedRows` and `ZeroRowExtractions` keep their names, `FunctionName` dimension and record builder (`extractionMetricRecord`). Ephemeral stacks stop publishing them. No ephemeral alarm reads them.

### 7.5 Free AWS metrics relied on

| Namespace | Metrics | Used for |
| --- | --- | --- |
| `AWS/States` | `ExecutionsStarted`, `ExecutionsSucceeded`, `ExecutionsFailed`, `ExecutionsTimedOut`, `ExecutionTime` | `ExecutionsStarted` on the ingest workflow is the count of emails received: SES stores every message, and each stored message starts one execution. SES publishes no metric for received mail. The others give final failures. The failure and timeout alarms already exist. |
| `AWS/Lambda` | `Errors`, `Duration`, `Throttles`, `ConcurrentExecutions` | Per-function health. The `Errors` alarms already exist. |
| `AWS/Textract` | `SuccessfulRequestCount`, `ThrottledCount`, `UserErrorCount`, `ServerErrorCount`, `ResponseTime`, with `Operation=AnalyzeDocument` | Textract call rate and errors as Textract sees them, including calls that never returned to the Lambda. They are account-wide, so they include calls from every stack in the account. |
| `AWS/SQS` | `ApproximateNumberOfMessagesVisible` on the workflow DLQ | EventBridge could not start an execution. An execution that starts and then fails never reaches the DLQ; Q2 and `ExecutionsFailed` cover it. The alarm already exists. |

## 8. Logs Insights queries

Q1 to Q5 and Q7 run over the `ProcessEmail`, `ExtractText`, `WriteExtractedCsv` and `WriteGamertagCsvs` log groups, and Q2 also over the ingest workflow log group (`/aws/vendedlogs/states/<resourcePrefix>`). Q6 runs over all six function log groups. In dev and prod the stack saves each as a `logs.QueryDefinition` named `<resourcePrefix>/<id>`. Developers paste them from this section (§8.2).

| ID | Purpose | Query |
| --- | --- | --- |
| Q1 | Trace one submission or execution | `filter event = "stage.completed" and (submissionId = "<id>" or executionId = "<execution ARN>") \| sort @timestamp asc \| fields @timestamp, Stage, workflow, outcome, screenshotId, runId, retryCount, durationMs, errorName, ErrorClass, rejectionCodes, attachmentRejectionCodes, fileCount, xrayTraceId` |
| Q2 | Status of each ingest execution | `filter (event = "stage.completed" and workflow = "INGEST") or type in ["ExecutionFailed", "ExecutionTimedOut", "ExecutionAborted"] \| fields coalesce(executionId, execution_arn) as execution \| stats max(screenshotCount) as expected, count_distinct(exportedScreenshotId) as exported, count(completedSubmissionId) as completed, max(fileCount) as gamertagCsvs, count(rejectionCodes) as rejected, count(execution_arn) as ended, min(@timestamp) as firstSeen, max(@timestamp) as lastSeen by execution \| sort lastSeen desc` |
| Q3 | Stage funnel | `filter event = "stage.completed" \| stats count_distinct(executionId) as executions, count_distinct(screenshotId) as screenshots by Stage, workflow, outcome` |
| Q4 | Per-stage latency | `filter event = "stage.completed" and outcome = "OK" \| stats pct(durationMs, 50) as p50, pct(durationMs, 95) as p95, max(durationMs) as worst, pct(endToEndMs, 95) as e2eP95 by Stage` |
| Q5 | Failed attempts and rejections | `filter event = "stage.completed" and (outcome != "OK" or ispresent(attachmentRejectionCodes)) \| stats count() as events, count_distinct(executionId) as executions by Stage, outcome, ErrorClass, errorName, rejectionCodes, attachmentRejectionCodes \| sort events desc` |
| Q6 | Cold starts and memory | `filter type = "platform.report" \| stats count(record.metrics.initDurationMs) as coldStarts, max(record.metrics.maxMemoryUsedMB / record.metrics.memorySizeMB) as memoryPeak, pct(record.metrics.durationMs, 95) as p95 by @log` |
| Q7 | Errors per hour | `filter event = "stage.completed" and outcome = "ERROR" \| stats count() as errors by bin(1h) as hour, Stage, ErrorClass, errorName \| sort hour desc, errors desc` |

Q5 counts attempts. An extraction that fails at retry 0 and succeeds at retry 1 still appears once in Q5, and a non-retryable failure appears once at retry 0. Q2 decides whether an execution finally failed. To count one code across combinations, filter on it, for example `filter rejectionCodes like /SENDER_NOT_ALLOWED/`.

Logs Insights bills by bytes scanned. Queries default to the last 24 hours. Q1 for an older submission should use the narrowest range that covers it.

### 8.1 Execution status rules

Q2 aggregates per execution and never uses the order of events, so screenshot branches can finish in any order. Read each row with the first rule that matches:

| Condition | Status | Meaning |
| --- | --- | --- |
| `rejected` > 0 | `REJECTED` | `process-email` rejected the whole submission, and the execution ended as succeeded. |
| `ended` > 0 | `FAILED` | Step Functions recorded a failure, timeout or abort. This includes a `process-email` failure before `submissionId` exists, a branch that exhausted its retries, a `write-gamertag-csvs` failure, and an invocation that timed out or ran out of memory without writing an event. |
| `completed` > 0 | `COMPLETE` | `write-gamertag-csvs` stored every gamertag CSV. `gamertagCsvs` is how many. |
| otherwise | `IN_PROGRESS` | `exported` of `expected` screenshots have their CSV, the gamertag step has not finished, and Step Functions has not recorded an end. |

The ingest workflow times out after 15 minutes, which writes an `ExecutionTimedOut` record. A row still `IN_PROGRESS` after `firstSeen` plus 15 minutes means telemetry was lost, and the execution history in the Step Functions console is the fallback. Use Q1 with the row's `execution` to see which stage is missing.

### 8.2 Developer access to ephemeral logs

Ephemeral stacks write logs and nothing else. A developer reads them with the `mcc-dev` profile after P1.4 adds this statement to `docs/self-hosting/policies/local-cdk-deployer-dev.json.template` and an operator updates the `MccStatsSuiteLocalCdkDeploy` inline policy:

```json
{
  "Sid": "ReadEphemeralMatchToCsvLogs",
  "Effect": "Allow",
  "Action": [
    "logs:DescribeLogStreams",
    "logs:FilterLogEvents",
    "logs:GetLogEvents",
    "logs:GetLogGroupFields",
    "logs:GetQueryResults",
    "logs:StartLiveTail",
    "logs:StartQuery"
  ],
  "Resource": [
    "arn:aws:logs:AWS_REGION:DEV_ACCOUNT_ID:log-group:/aws/lambda/match-to-csv-e-*",
    "arn:aws:logs:AWS_REGION:DEV_ACCOUNT_ID:log-group:/aws/lambda/match-to-csv-e-*:*",
    "arn:aws:logs:AWS_REGION:DEV_ACCOUNT_ID:log-group:/aws/vendedlogs/states/match-to-csv-e-*",
    "arn:aws:logs:AWS_REGION:DEV_ACCOUNT_ID:log-group:/aws/vendedlogs/states/match-to-csv-e-*:*"
  ]
}
```

The `:*` resources cover log streams, which `GetLogEvents` authorizes against. `GetQueryResults` sits in this statement because it authorizes against the queried log groups, so a developer cannot read the results of a query over stable dev logs even with its query ID. `GetLogGroupFields` is what the Logs Insights console calls to list fields, and console queries fail without it.

A second statement allows `logs:DescribeLogGroups` and `logs:StopQuery` on `*`, because those actions support no resource type. `DescribeLogGroups` reveals log group names in the dev account, not their contents. `logs:DescribeQueries` is not granted, because it would list every query ID in the account. The console's query history is unavailable as a result.

With that access, a developer tails one function or runs a query:

```console
aws logs tail /aws/lambda/match-to-csv-e-<name>-ExtractText --follow --profile mcc-dev
aws logs start-query --profile mcc-dev \
  --log-group-names /aws/lambda/match-to-csv-e-<name>-ProcessEmail /aws/lambda/match-to-csv-e-<name>-ExtractText /aws/lambda/match-to-csv-e-<name>-WriteExtractedCsv /aws/lambda/match-to-csv-e-<name>-WriteGamertagCsvs /aws/vendedlogs/states/match-to-csv-e-<name> \
  --start-time "$(date -v-1H +%s)" --end-time "$(date +%s)" --query-string '<Q2>'
aws logs get-query-results --query-id <id> --profile mcc-dev
```

The CloudWatch console's Logs Insights and Live Tail pages work with the same access.

## 9. Alarms and dashboard

### 9.1 Alarms added

Every alarm is created only in dev and prod, publishes to the existing alarm topic, and treats missing data as not breaching, like the existing alarms.

| Alarm | Metric and statistic | Period, evaluation | Threshold |
| --- | --- | --- | --- |
| `EndToEndLatencyAlarm` | `EndToEndLatency`, `Stage=write-gamertag-csvs`, p95 | 1 hour, 1 of 1 | greater than 300000 ms (5 minutes). The workflow timeout is 15 minutes. |
| `OcrMeanConfidenceAlarm` | `OcrMeanConfidence`, `Stage=extract`, Average | 6 hours, 1 of 1 | less than 90 percent. Cells under 95 are already flagged for review, so a mean under 90 means most screenshots need review. |
| `TextractThrottledAlarm` | `AWS/Textract` `ThrottledCount`, `Operation=AnalyzeDocument`, Sum | 1 hour, 1 of 1 | greater than 0. The workflow retries throttled calls, so a throttle is a warning before it becomes a failure. |
| `UnmatchedPlayerRateAlarm` | Metric math over the three `PlayerRows` Sums with `Stage=extract`: `FILL(unmatched, 0) / (FILL(exact, 0) + FILL(resolved, 0) + FILL(unmatched, 0))` | 6 hours, 1 of 1 | greater than 0.2. A rising rate means the roster is missing players or OCR misreads gamertags. Each term is zero-filled because a status with no rows writes no breakdown record (§7.1), and metric math without `FILL` has no value when any series is missing. |
| `MatchDateReplyFailedAlarm` | `MatchDateReplyFailed`, `Stage=process-email`, Sum | 1 hour, 1 of 1 | greater than 0. An allowed sender sent a bad date and was not told. |

The thresholds are starting values. Tuning them after real traffic is an ordinary code change.

```typescript
  | 'TEXTRACT_THROTTLED'

  | 'INTEGRITY'
  | 'CONFIGURATION'
  | 'STORAGE'
  | 'OTHER';

  stage: Stage;
  outcome: StageOutcome;
  durationMs: number;

  properties: Record<string, string | number>;

  };
}
```

`publishStageEvent` derives `ErrorClass` and `StageErrors` from `errorName` on an `ERROR` event, and writes one breakdown record per non-zero entry of `breakdowns`.

## 14. Security and privacy

1. Events and breakdown records carry identifiers, counts, codes, timings and confidence only. They never contain image bytes, OCR text, extracted rows, gamertags, gamertag CSV file names, email subjects or bodies, sender or recipient addresses, the sender allowlist, or SSM parameter values.
2. `errorName` holds the error's `name` and never its message, because provider and parser messages can echo input.
3. `trace` and `receivedAt` come from the state machine, but handlers still validate them before logging, because a direct invocation can supply any value.
4. The Step Functions change removes execution data, including extracted rows, from logs.
5. The developer grant (§8.2) reads only `match-to-csv-e-*` log groups in the dev account. It never covers stable dev log groups, prod, metrics or X-Ray, and the permission set stays assigned to the dev account only.

## 15. Observability

This whole spec is the observability design. The audit record for "what happened to this input" stays the S3 evidence events (`SUBMISSION_*`, `RUN_*`). Q1 is the fast index into them.

## 17. Acceptance criteria

- [ ] Every `process-email`, `extract-text`, `write-extracted-csv` and `write-gamertag-csvs` invocation writes exactly one §6 event, including `process-email` failures before `submissionId` exists.
- [ ] In dev and prod the metrics in §7.2 appear with the dimensions it lists, every dimension value comes from its fixed list, and `ExtractedRows`, `ZeroRowExtractions` and the zero-row alarm are unchanged.
- [ ] A rejected submission ends its execution as succeeded and fires neither `ExecutionsFailed` nor the ProcessEmail `Errors` alarm. Its `SUBMISSION_REJECTED` evidence event is unchanged.
- [ ] Q2 reports `COMPLETE` only after `write-gamertag-csvs` succeeds.
- [ ] The dashboard shows every §9.2 row, including the two Logs Insights tables.
- [ ] Ephemeral stacks publish no EMF metrics and create no alarms, query definitions or dashboard.
- [ ] A developer with the `mcc-dev` profile can tail and query an ephemeral stack's log groups from the CLI and the console, and cannot read stable dev log groups or the results of queries over them.
- [ ] Deploying any single slice to dev or prod keeps `ExtractedRows` and `ZeroRowExtractions` publishing.
- [ ] Q2 reports each §16.3 case with the status §8.1 gives it.
- [ ] The ingest workflow logs at `ERROR` without execution data.
- [ ] No event contains the content §14 excludes.
- [ ] X-Ray active tracing is unchanged, and every existing alarm keeps its metric and threshold.

## 18. Risks and accepted limitations

1. **EMF under the JSON log format:** if the runtime wraps stdout lines under `loggingFormat: JSON`, metrics stop appearing. Ephemeral stacks cannot show this, because they publish no metrics, so the operator check after the first dev deploy (§16.3) catches it. The fallback is to keep the text format and drop only the application log level change.
2. **Logs expire:** after retention, Q1 and Q2 return nothing for old submissions. Accepted. The S3 evidence events keep the full history.
3. **Attempts, not outcomes:** `StageErrors`, Q5 and Q7 count failed attempts, including ones a retry later fixed. Accepted. Q2 and `AWS/States` `ExecutionsFailed` report final failures.
4. **Sparse data:** at low volume the percentile alarm evaluates few points and can fire on one slow submission. Accepted. A single 5-minute delay is worth knowing about at this scale.
5. **Lost events:** an invocation that times out or runs out of memory writes no event. Q2 still marks the execution `FAILED` from the Step Functions record, and Q1 shows the last event that was written.
6. **Manual permission update:** the §8.2 grant takes effect only after an operator updates the permission set in IAM Identity Center. Until then developers cannot read ephemeral logs.
7. **No developer metrics or X-Ray:** developers see logs only. Accepted. Metric behavior is checked in dev, and `xrayTraceId` is for operators.
8. **No telemetry for operator tools:** `compare-runs` and `materialize-training-data` write no events (P3.1).
9. **Reasons overlap:** a submission with several rejection codes counts once under each `Reason`, so the reasons can sum to more than `SubmissionsRejected`. Accepted. The total and the breakdown are separate metrics.
10. **Unmapped errors:** a new error name counts under `OTHER` until someone adds it to the §7.3 table. Q7 still shows the raw name.
11. **Replays move quality alarms:** a bulk replay of old screenshots, such as after a roster change, adds to `OcrMeanConfidence` and `PlayerRows` and can trip `OcrMeanConfidenceAlarm` or `UnmatchedPlayerRateAlarm`. Accepted. The operator who starts a bulk replay expects the alarm, and Q3 separates replay events by `workflow`.
12. **Account-wide Textract metrics:** the `AWS/Textract` metrics and `TextractThrottledAlarm` include ephemeral stacks in the dev account. Accepted. In prod they cover only the prod stack.

### 20.4 Dependency order

P0.1 comes first, and P1.4 can run at any time. P0.2, P1.1 and P1.6 need P0.1. P1.3 needs P0.2. P1.2 and P1.5 need P0.2, P1.1 and P1.3, so ephemeral stacks have metrics turned off before any of them emits a stage event. P2.1 needs P1.2, P1.3, P1.5 and P1.6 and comes last. P1.6 is useful on its own: once it deploys, the existing failure alarms stop firing on rejected mail. The first useful observability milestone is P1.2 and P1.5 with P1.4, when a developer can run Q1 and Q2 against their own stack.
